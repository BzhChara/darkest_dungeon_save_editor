# Darkest Dungeon Save Editor

一个独立的 Windows 离线存档修改器。项目从 `DarkestDungeonRuntimeFramework` 中只抽取存档编解码、内容目录和安全写入思想，不依赖其 RuntimeHook、ManagedAction、Boss Gauntlet 或任务板实现。

已确认的内容覆盖、人物、怪癖、饰品、HP 计算、存档安全边界与证据等级统一记录在英文版 [内容目录与存档写入规则](docs/content-save-rules.md)；界面基准、标题动画修复和视觉回归要求记录在 [视觉设计与 QA](docs/design-qa.md)。README 描述当前能力；规则文档同时区分已实现行为、审核结论和仍需实机验证的项目。

## 当前能力

- 程序启动时游戏、Workshop、本地 Mod 和存档路径都保持为空，不会使用开发者本机路径。用户点击“自动发现”后，程序才从 Steam 注册表与 `libraryfolders.vdf` 定位 Darkest Dungeon 和 Steam `profile_*` 存档；存档优先选择 `profile_0`，不存在时才回退到发现列表中的第一个档案。自动发现会按该游戏所在 Steam 库填入 `steamapps\workshop\content\262060`，并按游戏目录填入 `DarkestDungeon\mods`；所有路径之后都可手动修改，本地 Mod 目录也可改为包含多个 Mod 的其他根目录或单个含 `project.xml` 的 Mod 目录。
- 从 `persist.game.json/base_root.applied_ugcs_1_0` 读取当前档案实际启用的 Mod 及界面自上而下的数字顺序；文件覆盖按游戏规则从底部 Mod 向顶部 Mod 应用。
- 从原版、档案启用的官方 DLC、Workshop Mod 和本地 `mods` 内容读取可计数物品、饰品、人物与怪癖；禁用内容不会进入目录。物品目录会先检测当前档案状态：小镇中读取 `wallet` 的金币、祖产、星晶、建筑图纸、Mod 货币，以及 `estate_items.items` 的血酿、邀请函和 Mod 庄园物品；副本中改为读取当前 `party.inventory.items`，显示火把、解毒剂、食物、宝石、祖产、任务物品和活动 Mod 的同类定义。同一定义可以合法地同时存在于两种目录中，程序会分别读取各自存档里的数量，不会因它可在小镇修改就把它从副本目录排除。饰品副本（包括当前背包中已经携带的饰品）仍由独立饰品功能处理，任意进度数值不会混入物品目录。Mod 物品按当前场景分别建立引用链：小镇目录接受城镇事件奖励或消耗、建筑与升级费用、庄园目标，以及明确允许手动配给等庄园持有入口；副本目录只接受配给、技能、英雄、怪物、任务、场景或掉落等能够进入背包的入口，单纯的城镇奖励、建筑费用或庄园货币引用不会再放行副本物品。当前目标存档不存在且在对应场景不可达的旧定义默认隐藏；勾选“显示当前场景隐藏项”后，列表会切换为只显示这些定义，取消勾选则恢复正常内容。属于数量功能范围且在当前目标存档中实际存在的条目始终显示，即使保存数量为零。物品、人物、怪癖和饰品同时解析 `schinese` 与 `english` 名称；缺少某种语言时显示 `—`，不会伪造翻译。
- 物品功能位于饰品左侧，使用绝对“目标数量”。小镇模式保持原有庄园规则：已有条目只修改 `amount`，缺失条目按真实 `wallet` 或庄园物品结构创建，`.base_stack_limit` 不被误当成庄园总上限。副本模式则直接修改当前 `persist.raid.json`：先补满同物品现有堆叠，再按活动 `.base_stack_limit` 拆分并占用编号最小的空格；动态读取活动 `raid.max_slots`，背包满时拒绝且绝不覆盖已有格子，目标为 0 时仅移除对应物品堆叠。任务物品会给出一句目标风险提示。目录加载后若进出副本、物品数量、Mod 配置、Manifest、所选定义或背包容量发生变化，旧预览会失效。预览执行 DSON 编码—解码全量一致性校验；应用时只替换当前场景的目标存档，并完整备份所有 `persist*.json`。
- 战斗页在当前档案处于副本时，从稳定的 `persist.map.json` 与 `persist.raid.json` 文件对显示完整全局地图；房间、普通走廊、探索状态、可编辑内容和队伍位置均使用游戏安装目录中的原版地图素材，游戏写盘后自动安全重读，不读取进程内存。原版隐藏饥饿节点不显示，也不提供新建、替换或删除，但所在走廊格仍可作为移动目标且不会改变节点。右键“删除”会彻底清空所选格子的完整待处理事件、战斗索引及奇物、陷阱、障碍资源绑定，同时保留探索状态；已经完成但仍显示使用后模型的格子也可再次删除残留。所有已实现的战斗写入和附加内容替换都会在同一次事务中覆盖或清空冲突绑定，不需要用户先行删除。带有效普通房间战斗索引的非出生、非最终房间会额外显示“战斗附加内容”：奇物与宝箱分别从当前档案启用内容的 `room_curios`、`room_treasures` 建立双语搜索目录，可在纯战斗上追加、同类替换或在两类之间切换，也可移除附加内容恢复纯战斗；整个过程只更换复合内容值与奇物资源哈希，原有 `mash_type=1`、`mash_index` 和敌方组合保持不变。该入口不会出现在走廊、固定首领或出生/最终房间。当前副本某一 `mash_type` 只有一个有效标准文件时，普通战斗仍可使用可证明的类型内零基索引；多个文件共同扩展时不猜测索引。战斗菜单还会从当前档案实际启用的 Base、DLC 与 Mod 中收集敌方定义齐全的条件/额外 hall/room 遭遇、显式游荡条目和固定 `boss:` 组合，并提供“游荡首领 / 特殊遭遇”和“固定首领”两个全局搜索入口；前者把游荡首领、游荡怪群、收藏家这类条件首领及其他条件/额外战斗放在同一张表中，再用“遭遇类型”逐行说明来源机制。组合列同时显示游戏提供的简中敌方名与原始敌方 ID；某个成员缺少简中名称时显示 `—`，不伪造翻译；内部游荡 ID 不作为用户列显示。固定首领搜索覆盖当前及跨地图完整组合；当前表已有的组合直接写入，跨地图组合自动通过托管 Encounter Bridge 建立稳定索引。用户不再接触索引或执行复制、启用、置顶、重载、战后删除等步骤。编辑器在后台为每个档案维护一个常驻的托管 Encounter Bridge：首次选择时自动安装到配置的本地 Mod 根目录并在当前档案中启用、置顶，以后把同一目标地区/难度/类型下的完整敌方组合仅追加一次并永久复用，既有索引永不重排；实际 `.mash.darkest` 和 `ddse-managed-encounter-bridge.json` 同时保存稳定映射。托管 Bridge 保留原始 hall/room/boss 类型和敌方顺序，不自动缩放跨难度组合，也不会由编辑器自动禁用或删除；活动 Mod 集合或顺序变化导致旧表基础不再可证明时会拒绝追加而不是重建可能仍被存档引用的索引。右键“移动队伍到此”会按房间或走廊的正反方向同步副本位置字段，但不补走路线、不改探索状态或目标内容，也不保证触发依赖“走入格子”的陷阱或障碍事件。这些写入都会要求游戏已关闭，拒绝战斗、露营、待领取战利品、门口/传送及脚本波次等过渡状态，并在确认后执行有效内容与 Mod 配置指纹、双文件哈希保护、DSON 回环、完整档案备份与失败回滚。顶部“强制返回城镇”用于 Mod 测试救档：程序验证当前游戏、地图与副本存档，完整备份档案后仅将 `persist.game.json` 的 `inraid` 设为 `false`、`raiddungeon` 设为 `none`，让游戏下次读档直接进入城镇；它不模拟正常撤退，也不额外结算或改写人物、任务、周数、背包、地图和副本文件。独立奇物、独立宝箱、陷阱、障碍、伏击复合事件和未解析的 named/script 遭遇的新建/替换目前仍只做界面预览。
- 普通战斗不再提供随机预览或逐项子菜单；房间和走廊都会打开与特殊遭遇相同的双语搜索窗口。目录覆盖当前档案启用内容中的跨地区标准组合，保持原始 `hall`/`room` 类型和具体难度；当前表已有组合直接写入，其余组合由托管 Encounter Bridge 建立稳定索引。普通战斗、特殊遭遇和固定首领入口末尾均不再显示装饰性省略号。
- 同一套活动内容覆盖顺序也用于解析 `trinket_storage.max_slots`，解析时忽略 `.darkest` 文件的 `//` 行注释，并要求生效条目只有一个完整的正整数 `max_slots` token。饰品预览显示仓库内该 ID 的当前/结果数量、定义上限，以及仓库总槽位的当前/结果/有效容量；定义 `limit=0` 显示为“无限”。控制台模式允许用户显式写入超过单种饰品定义上限的普通副本并给出醒目警告，但核心写入链路会阻止超过当前活动配置的仓库总槽位；若最高优先级容量缺失、无效或存在无法消解的冲突，则直接禁用饰品预览与应用，不回退到原版容量。装备在英雄身上的副本不计入这里显示的仓库内数量。
- 饰品预览会保存所选档案的 `persist.game.json` 哈希、活动内容来源、所有活动 Workshop/本地 Mod 的 `modfiles.txt` 存在状态与哈希、生效容量文件和所选饰品定义文件指纹；应用前与最终替换前都会重建相关目录并核对定义。最终替换阶段会对这些已存在的 Manifest 和三个来源文件加只读锁，并在真实 estate 读锁内再次重验后执行原子替换。预览后若 Mod/DLC 状态、Manifest、所选饰品定义、容量文件、容量来源、有效槽位或真实存档发生变化，旧预览会被拒绝，必须重新加载目录并生成预览。
- 官方 DLC 的包根共享内容与 `features/<name>` 分开处理；`districts`、`flagellant`、`fires_edge`、`duelist`、`runaway` 等 feature 只有在当前档案明确启用时才进入目录。
- Workshop Mod 按工坊 ID 映射；本地 Mod 会同时扫描默认 `游戏目录\mods`、`游戏目录\dlc` 与可选额外目录，再按 `project.xml` 的 `Title` 映射。重叠目录会去重，缺失或同名歧义来源只报告、不猜测。
- 内容目录先按规范化相对路径处理 `原版 → DLC → Mod` 文件覆盖；Mod 内底部先应用、顶部最终保留。同一路径的来源链会保留用于诊断。来源列显示内容起源：原版物品、人物、饰品或怪癖被 Mod 覆盖时仍标记“原版”，并同时注明当前实际覆盖它的 Workshop/本地 Mod，不再把两种含义混成单个 Mod 来源。物品、饰品和怪癖会进一步按条目 ID 核对来源链；Mod 在覆盖文件中新增、但官方文件从未声明过的 ID 只标记为该 Mod，不会误报为原版内容。人物相关的 hero/effect/quirk/buff/event/upgrade ID 即使来自不同文件，语义相同也会合并；语义不同时继续使用相同的活动内容优先级选出胜者。只有同一最高优先级仍存在不同定义时才保持未解析。不同路径的重复饰品仍采用更保守的只读策略，不能进入存档预览。
- 人物目录会按活动内容优先级解析完整 `.info.darkest`，再叠加同职业的局部 `.override.darkest`；局部装备行只覆盖实际出现的 HP/升级代码，`generation_guaranteed=false` 可以撤销低层标记，技能的 `effect` 与各类 `*_effects` 也按各自字段替换而不会误删未触及字段。修改原版职业但未携带美术的 Mod 会继续继承仍然生效的低层皮肤目录。目录同时读取生成规则、各级武器/护甲、连续皮肤配色、0 级战斗技能、无值的 `generation_guaranteed` 标记、露营技能、`bonus_recruit` 城镇事件，以及“职业技能 → effect → `random_chance=0` 怪癖”的后续玩法线索。列表中的“游戏自然 / 编辑器手动”表示游戏能自然刷新且编辑器也能手动创建，“仅编辑器手动”表示 `is_generation_enabled=false`、游戏不自然刷新但模板仍可手动使用；模板未声明该标志时显示“自然状态未知 / 编辑器手动”，不会擅自推断。“自然怪癖范围”只是游戏自然生成时的正负怪癖数量范围，不限制玩家在编辑器中的主动选择。后续玩法线索不属于初始怪癖，也不会作为人物创建字段。
- 编辑器从当前档案的 `game_mode` 读取有效 `resolve_level_thresholds`，再把职业 `.info.darkest` 的装备 rank 与对应 `.upgrades.json` 的 `prerequisite_resolve_level` 组合成 0～满级模板。升级模板兼容原版 `upgrades/heroes/<hero>.upgrades.json` 和 Mod 常用的 `upgrades/<hero>.upgrades.json`。同一优先级存在多份模板时，只有一份对活动人物的精确技能树 ID 与装备代码具有唯一更高兼容性时才选中，平局仍拒绝猜测。玩家选择等级后，`resolveXp`、`weapon_rank`、`armour_rank` 和护甲基础 HP 会联动写入；同时按当前有效 upgrade 模板，把该等级已经满足前置条件的武器、护甲和每一个战斗技能购买链写入 `persist.upgrades.json`。露营技能使用游戏的隐式 `<职业 ID>.<露营技能 ID>` 购买树与 requirement code `0`，为活动内容中该职业可用的全部共享及职业露营技能写入解锁记录。因此生成的人物会在该等级范围内全战斗技能、全露营技能解锁，0 级也包含每棵战斗技能树的基础购买项。若人物文件明确只定义某技能的 0 级且没有任何更高等级，缺失升级树时按真实存档形状补 `<职业>.<技能>/code=0`；多级技能缺树或对应树在所选等级没有可购买 requirement 仍会拒绝生成。当前装备的技能数量仍按职业/Mod 自己的生成与选择模板决定，不会把“已解锁”误写成“全部同时装备”，也不会硬编码成原版常见的 4 个。树 ID 使用游戏已有的名称哈希规则，requirement code 原样且区分大小写地取自模板，不假定必须是数字；由于存档格式本身只容纳一个 ASCII 字符，多字符或非 ASCII code 会明确拒绝而不会静默截断，不同树 ID 的游戏哈希碰撞也会阻止写入。原版与模板完整的活动 Mod 职业共用同一套解析逻辑。不要求 roster 已经拥有该职业，也不挤占或改写现有人物。
- 候选人物默认不添加怪癖；玩家可显式选择 0 到多个初始怪癖。目录把“是否属于自然随机池”与“是否能安全显式写入”分开：结构已验证的固定/特殊怪癖即使 `random_chance=0` 也可以选择；控制台模式不执行职业模板中的 `incompatible_class_ids`，因此任何已识别且可直接写入的怪癖都可选给任意职业。普通疾病使用与怪癖相同的马车记录结构并允许选择，独立执行原版最多 3 个疾病的规则，不占正负怪癖各 5 个的名额。达到正面、负面或疾病上限后，目录行不会重复填入“再加一项”的配额原因；顶部计数和实际点击拦截负责说明上限，行内动态不可用原因只保留真正的 `incompatible_quirks` 互斥。进化怪癖会读取各自的 `evolution_duration_min`/`max`，按生成 seed 与怪癖 ID 得到独立稳定的区间内初始值并写入 `evolution_duration_remaining`；固定区间和作者显式配置的 `0–0` 会原样保留，不会再依赖游戏补初始化。缺少上下界、范围颠倒、非整数，或既无目标也未声明到期死亡的进化配置会保留显示但禁止选择。`singleton` 作为定义上限 1，预览统计当前 roster 与普通、碎片等全部马车候选池中的同 ID 怪癖，再加上本次候选；只有结果大于 1 时才在与饰品相同的风险区域警告并保留写入能力。正数 `roster_limit` 是游戏招募阶段对已拥有同怪癖英雄数的限制；编辑器只生成马车候选，没有改变 roster，因此不计数、不警告也不阻止，玩家招募时由游戏原逻辑执行上限。重复定义和未知 HP 规则仍禁止选择。非 HP Buff 的属性效果不在存档候选中预计算，交给游戏运行时应用，因此其重复或覆盖不会单独阻止怪癖；缺失或同优先级未解析的 `max_hp` Buff 仍会阻止写入。已识别的固定值与百分比 HP Buff 按游戏的 `(所选等级护甲 HP + 固定值合计) × (1 + 百分比合计)` 计算初始满血；`always` 与空饰品候选下的 `no_trinkets` 在生成时生效，`afflicted`、`in_mode`、`lightabove` 只记录怪癖并交由游戏在对应运行时条件下应用。编辑器还会检查所有已识别条件的可达组合，任何可能令固定项或倍率降到 0 以下的选择都会阻止。怪癖 Buff 不会写进 `actor.buff_group`，因此不会和游戏运行时效果重复计算。
- 战斗技能先保留 0 级必选技能，再随机选择；候选保存数量取生成数量与选择上限的较小值。候选 JSON 中的技能映射仍保持游戏原生的 0 值，技能等级与露营技能解锁状态由 `persist.upgrades.json` 的个人购买记录表达，不会把“已解锁”和“当前装备”混写。技能伤害、命中、效果或其他职业战斗属性不复制进存档，而由游戏在载入时从当前最高优先级的原版/Mod 模板解析。露营技能按共享/职业池分别选择当前装备项，共享池不足时按真实样本少取，不用职业技能补位；无论当前装备哪些，活动内容中识别到的全部可用露营技能都会解锁。
- 人物预览同时修改临时 `persist.town.json`、`persist.roster.json` 与 `persist.upgrades.json`：带有 `shard_hungry` 的候选追加到碎片马车，其余候选追加到普通马车；随后推进 `nextGuid`，并为同一个 GUID 追加等级对应的个人升级购买记录。预览和确认界面会明确显示实际目标马车。预览前、预览结束和提交期间会重建人物目录语义指纹；若活动 Mod/DLC、Manifest、职业、怪癖、等级阈值或升级模板发生变化，旧预览会被拒绝。三个文件都通过 DSON 编码—解码全量一致性校验后，才允许用户确认写入；提交顺序为 upgrades、roster、town，任何一步失败都会从完整备份回滚所有已替换文件，备份清单同时记录候选 XP、装备 rank 和个人升级记录数。
- 在临时工作区中按存档状态解码 `persist.estate.json` 或 `persist.raid.json`，修改用户明确选择的物品目标数量；普通饰品仍写入庄园仓库。
- 主窗口与怪癖选择窗口使用统一的暗黑地牢面板风格；Windows 原生标题栏和边框采用暗黑/暗红配色，石墨纹理以完整窗口铺设并透过半透明面板可见。这只改变呈现，不改变既有预览—确认—备份—提交步骤。
- 编码后再次解码，验证目标物品数量或饰品数量、档案概要和 DSON 修订字段。
- 只有用户再次确认后才覆盖当前操作对应的真实存档文件。
- 覆盖前检查游戏未运行、源文件哈希未变化，并备份 profile 目录下全部 `persist*.json`。

带 `quest_uses` 或 `trigger_limit` 的次数饰品可以生成，但编辑器只创建从未消耗过的初始实例：剩余次数取定义中的完整上限，任务内使用标记和变形状态均为初始值。渐进贴图、耗尽变形/销毁和附加效果仍由游戏按饰品定义处理；定义中的次数不是正整数时会禁止写入。

## 写入与恢复边界

1. “生成安全预览”只复制、解码、修改和编码临时工作区。
2. 预览生成后，如果原存档哈希发生变化，应用会被拒绝。
3. “应用到存档”会检查 `Darkest.exe` 未运行。
4. 写入前会在 `%LOCALAPPDATA%\DarkestDungeonSaveEditor\backups` 建立完整时间戳备份和清单。
5. 文件替换或最终哈希校验失败时，程序会尝试立即恢复备份。

当前人物能力只向马车候选池加入新人物：选择 `shard_hungry` 时进入碎片马车，否则进入普通马车。它不修改已拥有英雄、马车卡池历史、周数、铁匠铺升级、任务、城镇事件历史或游戏内容文件。高等级候选携带相应人物 XP、个人装备 rank 与个人技能/装备购买链，但不会替玩家解锁铁匠铺、公会等城镇建筑。“从陵墓归来”等事件会在后续阶段基于原版存档差异单独实现。

应用的阶段、异常、界面状态和完整目录提示会写入 `logs/app-日期.log`。内容加载后，底部运行日志会显示档案/模式/活动来源摘要，以及按当前小镇或副本场景区分的物品、隐藏项、背包格位、饰品、人物、怪癖、姓名和等级统计；副本已占格位按存档背包的全部条目计算，包括由独立饰品功能处理而不进入物品目录的随身饰品。这些信息不再挤占目录控件上方。持久日志还记录完整 Profile 路径、`persist.game.json` 与当前数量来源存档的 SHA-256，副本模式另记录庄园存档 SHA-256。开发运行时从程序目录向上定位 `DarkestDungeonSaveEditor.sln`，因此日志位于项目根目录的 `logs`；独立发布目录没有解决方案文件时，日志位于 EXE 同目录的 `logs`。界面最多展示前 30 条目录提示，日志保留全部提示。工作区和存档备份仍位于 `%LOCALAPPDATA%\DarkestDungeonSaveEditor`。

本机开发约定：用户已授权游戏界面的第 4 号存档作为可破坏测试档；其本机目录是 `profile_3`（界面从 1、目录从 0 编号）。需要启动游戏或验证真实写入时仍先自动备份并记录哈希；其他档案继续按正式存档处理。`DarkestDungeonRuntimeFramework` 中的参考项目和实验存档可作为只读证据与夹具来源，但其自定义插件优先级不等同于游戏原生 Mod 顺序。

英雄生成不以玩家已经拥有同职业实例为前提。活动内容中的 `.info.darkest` 提供职业生成规则、技能和装备定义，通用英雄存档结构来自真实马车候选。部分 Mod 会禁用随机怪癖，再由技能中带 `disease` 赋值的效果、或城镇事件在游戏运行时授予专属怪癖；目录只扫描这种实际赋值 Effect，普通战斗 Effect 不再产生无关冲突提示。人物、怪癖和饰品显示名同时支持容错 `.string_table.xml` 与游戏编译后的 English/简中 `.loc2`；同一内容来源同时提供两种格式时，以游戏实际读取的 `.loc2` 为准。有 `modfiles.txt` 时仍补充读取 Mod 顶层 `localization` 目录内的直接 `.string_table.xml` 源表，用于兼容只把旧 `.loc` 写入清单、却保留可读 XML 源表的 Mod；不会递归进入 `unused` 或平台目录。LOC2 的编译颜色开始/结束标记可能跨字符串出现，因此分别剥离而不要求单条内成对；偏移、长度、NUL 和去除色码后的 UTF-8 仍严格检查，真正损坏或越界的二进制表只产生目录提示，不阻断其他文件。随机英雄姓名仍从可枚举键名的 XML 源表读取。清单中的 `.string_table.xml.unused` 和 `.loc2.unused` 不会被误当成活动文件。无 `modfiles.txt` 时会按标准内容目录回退扫描并为每个 Mod 输出一条可去重信息。职业若缺失连续装备 rank、对应升级代码或有效 HP，仍可在证据充分时保留 0 级模板，但不可选择无法证明的高等级。带 `singleton`、正数 `roster_limit` 的怪癖均允许显式写入；前者按 roster 与全部马车候选池做只警告的检查，后者不在马车生成阶段检查，由游戏在招募阶段执行。缺失或未解析的 HP Buff、未知条件型 HP 规则仍会阻止选择。结构完整且持续值有效的进化配置可以写入，未知或无效的进化配置仍会阻止选择。

`actor.buff_group_next_guid=2` 采用真实已保存马车候选中的最小观测值；它不参与 HP 计算，`buff_group` 仍保持为空。该结构已经通过 DSON 回环和第 4 号测试档实机载入：在完整备份后，编辑器向 `profile_3` 的普通马车加入 GUID 364 的原版蛮族战士 `Cumin`，游戏成功显示该候选，已拥有英雄仍为 36 人。

该候选以 `current_hp=23.4`、基础生命 26 和 `fragile`（生命上限 -10%）写入；游戏界面显示最大生命 24，并明确列出“基础 26 / 特质 -10%”，因此读取与显示链路没有重复计算怪癖效果。游戏加载并正常退出后没有改写 `persist.town.json` 或 `persist.roster.json`，所以这次验证尚不能证明游戏重新序列化后的 `buff_group_next_guid`、`buff_group` 或招募进入 roster 的结果。
