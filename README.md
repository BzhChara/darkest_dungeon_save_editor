# Darkest Dungeon Save Editor

A standalone Windows editor for offline Darkest Dungeon saves. The project draws only on the save codec, content catalogs, and guarded-write approach from `DarkestDungeonRuntimeFramework`. It does not depend on that project's RuntimeHook, ManagedAction, Boss Gauntlet, or quest-board implementation.

Confirmed content overlays, hero and quirk rules, trinkets, HP calculations, save-safety boundaries, and evidence levels are documented in [Content Catalog and Save Rules](docs/content-save-rules.md). UI baselines, title-animation fixes, and visual regression requirements are documented in [Visual Design and QA](docs/design-qa.md). This README describes current capabilities; the rule documents distinguish implemented behavior, review findings, and areas that still need live-game verification.

Current rules and design documents under `docs/` are versioned project documentation. Review reports, experiment records, and historical fix notes under `docs/change-history/` are local-only material: Git ignores that entire directory, and a new clone does not include it. Historical record names in the rule documents are provenance references, not links to files shipped with the project.

UI action names below are English descriptions of localized controls. The application still reads both English and Simplified Chinese game names; translating the documentation does not change the application's language.

## Download and run

The first public prerelease is [v0.1.0-beta.1](https://github.com/BzhChara/darkest_dungeon_save_editor/releases/tag/v0.1.0-beta.1). Download the **Windows x64 ZIP** from its assets, extract all files, and run `DarkestDungeonSaveEditor.App.exe`. The .NET 8 runtime is included; **Java 8 or newer must be installed separately and available on `PATH`**. The application UI is currently localized in Simplified Chinese.

See [Installation and first use](docs/release-installation.md) for requirements, checksum verification, backups and updates. This is a prerelease: keep a separate save backup and check the selected profile before editing. The **Source code** archives on GitHub require building the project.

## Current capabilities

### Loading and synchronization

- Items, trinkets, heroes/quirks, and battle maps share automatic synchronization after the selected profile is loaded. The first synchronization is part of **Load current save**: controls remain busy until it finishes. Subsequent game saves refresh quantities, context, and preview validation without repeated manual loading. Search, selection, entered quantities, hero level, and quirks are preserved within the same context; entering or leaving an expedition clears the previous context's item target. Relevant save changes invalidate old previews, which must then be regenerated.
- Save monitoring uses file notifications and a metadata check every 2 seconds. A lightweight save verification and retry of battle maintenance deferred while the game was running occur every 10 seconds. Ordinary save changes reuse the resource catalog. Resources are checked on initial load, Mod/DLC/game-mode changes, first entry into an uncached context, and editor-owned Bridge updates. While the window is active, a full resource check every 60 seconds covers encounters, monster definitions, Mod manifests, and other listed definitions, localization, and reference files. Periodic resource scans pause in the background; returning to the window triggers a check only when due. Content hashes still detect changes with unchanged length and modification time. Locked or partially written saves retain the previous snapshot and are retried automatically. Pre-write resource and save validation runs independently of these intervals. Snapshot reads use disk files only; actual writes require the game to be closed.
- If editor-placed battle bindings or Bridge formations become invalid or change index, maintenance removes invalid Bridge formations, recalculates retained indexes, and clears all battles in the current expedition that successful placement records prove were placed by the editor, including direct local placements. Curios, treasure, scouting state, and native battles are preserved. Maintenance runs during profile loading, synchronization, and pre-write map checks, with profile/Bridge backups and rollback on failure. It defers while the game is running, reads are incomplete, or indexes cannot be proved. See [Encounter Indexes and Automatic Maintenance](docs/encounter-runtime-order.md#automatic-editor-battle-maintenance-2026-09-07).
- Game, Workshop, local-Mod, and save paths start empty. **Auto discover** reads the Steam registry and `libraryfolders.vdf` to locate Darkest Dungeon and Steam `profile_*` saves. It selects `profile_0` when present, otherwise the first discovered profile. It derives `steamapps\workshop\content\262060` from the game's Steam library and `DarkestDungeon\mods` from the game directory. All paths remain editable; the local-Mod path can also be another multi-Mod root or one Mod directory containing `project.xml`.
- Explicit loading prepares missing `modfiles.txt` files for enabled Mods that can be located, using the game's official tool in `dont_submit` mode without uploading. Generation runs in an isolated copy, adds only the missing manifest to the original Mod, and preserves existing manifests. Files identical to the base game are omitted according to the official rules. This requires the game to be closed; a failure stops that load and reports the preparation record. All Mod resources then pass the manifest gate before each native consumer's directory, ordering, overlay, and duplicate-ID rules are applied. See [Resource Rules](docs/resource-duplicate-semantics.md).
- Enabled Mods and their numeric top-to-bottom UI order come from `persist.game.json/base_root.applied_ugcs_1_0`. File overlays are applied from the bottom Mod to the top Mod, matching the game.

### Items and trinkets

- Countable items, trinkets, heroes, and quirks come from the base game, profile-enabled official DLC, Workshop Mods, and local Mods. Disabled content is excluded. In town, the item catalog reads `wallet` currencies such as gold, heirlooms, shards, blueprints, and Mod currencies, plus blood, invitations, and Mod estate items in `estate_items.items`. During an expedition it reads the current `party.inventory.items`, including torches, antivenom, food, gems, heirlooms, quest items, and equivalent active-Mod definitions. One definition may belong to both contexts; each uses its own saved quantity. Trinket instances, including carried trinkets, remain under the separate trinket feature. Arbitrary progression values are not quantity items.
- Mod-item reachability is evaluated separately for each context. Town roots include town-event rewards or costs, building and upgrade costs, estate objectives, and explicit manual provisioning permission. Raid roots require an inventory-entry path through provisioning, skills, heroes, monsters, quests, scenes, or loot. A town reward, building cost, or estate currency reference alone does not establish raid reachability. An absent definition unreachable in the current context is hidden by default. **Show hidden items in current context** switches to an exclusive view of those hidden definitions; clearing it restores the normal list. In-scope entries physically present in the current target save remain visible even at zero quantity. Items, heroes, quirks, and trinkets resolve both `schinese` and `english` names; a missing language displays `—` without an invented translation.
- The item tab is to the left of trinkets and accepts an absolute **Target quantity**. In town, existing entries change only `amount`; missing entries use the actual `wallet` or estate-item structure. `.base_stack_limit` is not treated as an estate-wide cap. In raids, the editor changes the current `persist.raid.json`: fill existing matching stacks first, then split by the active `.base_stack_limit` into the lowest available slot indexes. The active `raid.max_slots` determines capacity. A full bag rejects the operation without overwriting occupied slots; a target of 0 removes only matching stacks. Quest items carry a short warning about quest implications. Changes to town/raid context, quantities, Mod configuration, manifests, the selected definition, or capacity invalidate an old preview. Preview uses a full DSON encode/decode equality check; apply replaces only the current context's target save and backs up every `persist*.json` file.
- The same active-content ordering resolves `trinket_storage.max_slots`. Parsing ignores `.darkest` `//` line comments and requires one complete positive-integer `max_slots` token in the effective entry. A trinket preview shows current/result counts for that ID in storage, the definition limit, and current/result/maximum storage slots. `limit=0` means unlimited. Console mode permits explicitly requested ordinary copies above the per-definition limit with a prominent warning, but the write pipeline enforces the active total storage capacity. Missing, invalid, or unresolved highest-priority capacity disables preview and apply rather than falling back to the base-game capacity. Equipped copies are excluded from the displayed storage count.
- Trinket previews capture the selected profile's `persist.game.json` hash, active sources, existence and hashes of every active Workshop/local Mod's `modfiles.txt`, and fingerprints of the effective capacity and selected definition files. Relevant catalogs and definitions are rebuilt before apply and before final replacement. Final replacement holds read locks on existing manifests and the three source files, then revalidates inside the real estate-save read lock before atomic replacement. Changes to Mod/DLC state, manifests, the definition, capacity file/provider/slots, or save reject an old preview. Save/configuration changes are handled by synchronization; resource-file changes are handled by periodic checks or an explicit reload.
- Trinkets with `quest_uses` or `trigger_limit` can be created only as pristine, unused instances. Remaining uses start at the definition's full limit, with initial quest-use and transformation state. Progressive textures, depletion transformations/destruction, and extra effects remain the game's responsibility. A non-positive or non-integer use limit blocks writing.

### Battle maps

- During an expedition, the battle workspace displays the complete map from a stable `persist.map.json`/`persist.raid.json` pair. Rooms, ordinary corridors, scouting state, editable content, and party position use original map assets from the game installation. Game writes trigger guarded disk rereads without process-memory access. Hunger tiles use the original hunger icon and, like the entrance, expose movement only. Moving the party does not change that tile's content.
- **Delete** clears the selected cell's entire pending event, mash binding, and curio/trap/obstacle bindings while preserving scouting state. Completed cells that retain a used model can also have their residual bindings removed. Implemented battle writes and attachment replacements replace or clear conflicting bindings within one transaction; a separate delete is unnecessary.
- **Battle attachments** appears for non-entrance, non-final ordinary rooms with a valid ordinary-room battle index. Curios and treasure chests have separate bilingual catalogs from the active `room_curios` and `room_treasures` pools. Users can add an attachment to plain combat, replace it, switch categories, or remove it to restore plain combat. Only the composite content value and curio hashes change; `mash_type=1`, `mash_index`, and the enemy formation remain intact. Corridors, fixed bosses, and entrance/final rooms do not expose this action.
- Direct battle placement requires a provable zero-based index within its `mash_type`; the editor does not guess indexes when multiple files extend a table. Global catalogs collect complete standard, conditional/additional hall/room, explicit roaming, and fixed `boss:` formations from active Base/DLC/Mod content. **Roaming bosses / Special encounters** combines roaming bosses, roaming groups, conditional bosses such as Collector, and other conditional/additional battles, with each row's exact mechanism shown under **Encounter type**. Compositions show game-provided Simplified Chinese enemy names and raw enemy IDs; a missing name is `—`. Internal roaming IDs are not user-facing columns.
- Ordinary battles, special encounters, and fixed bosses use bilingual composition search. There is no random-preview action or per-formation submenu. Ordinary formations retain their authored `hall`/`room` type and difficulty. Fixed-boss search includes complete current- and cross-region formations. A formation already in the current table writes directly; other eligible formations receive stable indexes through the managed Encounter Bridge. These menu actions have no decorative trailing ellipsis.
- The editor maintains a persistent, profile-scoped Encounter Bridge. First use installs it under the configured local-Mod root, enables it in the selected profile, and moves it to the top. Each complete formation is appended only once for its target region/difficulty/type and then reused; existing indexes are never reordered during append. Both the `.mash.darkest` file and `ddse-managed-encounter-bridge.json` retain the stable mapping. The Bridge preserves hall/room/boss type and enemy order, does not scale cross-difficulty formations, and is not automatically disabled or deleted. If a Mod-set/order change makes the old table basis unprovable, append is refused rather than rebuilding indexes a save may still reference. Users do not need to copy, enable, prioritize, reload, or remove carrier files manually.
- **Move party here** updates raid-position fields consistently with forward/reverse room or corridor direction. It does not traverse a route, change scouting or target content, or guarantee activation of events that depend on walking into a tile. Writes require the game to be closed and reject combat, camping, pending loot, doorway/teleport transitions, and scripted waves. After confirmation they validate effective content and Mod configuration, both displayed save hashes, DSON round trips, full-profile backups, and rollback.
- **Force return to town** is a recovery action for Mod testing. After validating the current game/map/raid saves and backing up the profile, it changes only `persist.game.json`: `inraid=false` and `raiddungeon=none`. The next load enters town. It does not simulate retreat, settle rewards, or additionally rewrite heroes, quests, week count, inventory, map, or raid saves.
- Standalone curios, room treasure chests, ordinary traps, and obstacles support actual create/replace writes. Curios and chests retain bilingual search and cross-region choice while respecting separate room/hall pools. Traps and obstacles use only resolved current-region resources and proceed directly to confirmation. Multiple valid choices use their positive authored weights; zero/invalid weights and other-region fallbacks are excluded. Curios write resource-ID hashes directly without adding a battle Bridge. Special traps/obstacles with ambush, teleport, or story behavior, ambush composites, and unresolved named/script encounters remain unsupported, with reasons logged. Hidden-room and story-map compatibility is still incomplete.

### Content catalogs and hero generation

- Official DLC package-root content is handled separately from `features/<name>`. Features such as `districts`, `flagellant`, `fires_edge`, `duelist`, and `runaway` are included only when explicitly enabled in the profile. Workshop Mods map by Workshop ID. Local Mods are discovered under the game's `mods` and `dlc` directories plus an optional extra root, then matched by `project.xml` `Title`. Overlapping roots are deduplicated; missing or ambiguous names are reported without guessing.
- File sources apply in `Base → DLC → Mod` order, with bottom Mods first and top Mods last. Diagnostic source chains are retained. Enumeration follows native query and slot-merging rules: a shorter path in an additional mount may replace a deeper path containing it, so different full paths are not always additive. Enumeration slots and the file ultimately opened are separate; repeated reads of one file retain separate slots. Fixed hero paths, additive curio queries, and the three base-only root props defaults use their corresponding consumers. Items/trinkets use first matching definitions; other consumers keep their verified duplicate-ID rules. See [Resource Rules](docs/resource-duplicate-semantics.md). Origin and current provider are tracked per ID: an ID added only by a Mod remains Mod content even inside an overridden official file.
- Hero catalogs resolve full `.info.darkest` definitions and then partial `.override.darkest` records by active priority. Partial equipment rows override only declared HP/upgrade codes; `generation_guaranteed=false` can clear a lower mark. Skill `effect` lists append according to native behavior; mode effects apply only to valid modes listed in the declaration. Skin directories merge across all active mounts, including standalone skin Mods; matching directory names count once and need not form a continuous sequence from A. Catalogs also read generation rules, equipment ranks, skin-index ranges, level-0 combat skills, guaranteed flags, camping skills, `bonus_recruit` events, and later-game clues from class skill → effect → `random_chance=0` quirk assignments.
- Recruitment labels distinguish enabled ordinary generation with manual editor creation, disabled ordinary generation with a still-usable manual template, and an undeclared/unknown generation flag. The editor does not infer natural availability from a missing flag. **Natural quirk range** describes natural positive/negative generation counts, not a cap on manual selection. Later-game assignment clues are not initial quirks or candidate-creation fields.
- Effective `resolve_level_thresholds` come from the profile's `game_mode`. Hero equipment ranks and `.upgrades.json` `prerequisite_resolve_level` values form templates from level 0 through the maximum. Both official `upgrades/heroes/<hero>.upgrades.json` and common Mod `upgrades/<hero>.upgrades.json` paths are supported. At equal priority, one template is selected only if it has uniquely higher compatibility with the active hero's exact skill-tree IDs and equipment codes; ties remain unresolved. Selecting a level updates `resolveXp`, `weapon_rank`, `armour_rank`, and base armor HP, and adds eligible personal weapon, armor, and combat-skill purchase chains to `persist.upgrades.json`.
- Camping unlocks use native implicit `<class ID>.<camping skill ID>` purchase trees with requirement code `0` for every active shared/class camping skill available to the hero. Generated heroes therefore have all combat skills unlocked through the selected level and all available camping skills unlocked; level 0 includes each combat tree's base purchase. A skill explicitly defined only at level 0, with no higher levels, may use an implicit `<class>.<skill>/code=0` purchase if its tree is absent. Multi-level skills without a tree, or trees without a purchasable requirement at the selected level, block generation. Equipped counts still follow class/Mod generation and selection templates, without equating unlocked skills with equipped skills or hard-coding four slots. Tree IDs use native name hashes. Requirement codes preserve literal case and need not be numeric, but the save format permits only one ASCII character; longer/non-ASCII codes and tree-hash collisions block writing. A previously owned hero of that class is not required, and existing heroes are not displaced or rewritten.
- New candidates start with no quirks; users can explicitly select zero or more. Natural random-pool membership is separate from safe explicit selection: verified fixed/special quirks with `random_chance=0` remain selectable. Console mode does not enforce class `incompatible_class_ids`. Diseases use the same candidate-record structure. Active shared rules determine positive, negative, and disease caps, with native defaults of 5, 5, and 3. A positive disease counts against positive and disease caps; a negative disease counts only against the disease cap. Each entry is stored once. Probabilities use native single precision: positive values that underflow to zero follow zero-probability classification and skill-clue rules; overflow remains uncertain. Reaching a cap is explained by top-level counts and click validation, not repeated quota warnings on every row. Dynamic row-level incompatibility reasons are reserved for actual `incompatible_quirks` conflicts.
- Evolution quirks read `evolution_duration_min`/`max` and derive an independent stable in-range initial value from the generation seed and quirk ID, writing `evolution_duration_remaining`. Fixed ranges, including explicit `0–0`, are preserved. Omitted integer fields use native zero defaults; entirely neutral defaults behave as ordinary quirks. Reversed ranges, negatives, non-integers, or non-neutral configurations with neither a target nor expiry death remain visible but unselectable. A `singleton` has a definition limit of 1: preview counts the same ID in the roster and every stagecoach pool, plus the new candidate, and warns only when the result exceeds 1 while retaining write support. A positive `roster_limit` is a recruitment-time limit on owned heroes; candidate generation neither counts nor warns on it, leaving enforcement to the game when recruited.
- Duplicate definitions and unknown HP rules still block selection. Non-HP Buff effects are applied by the game at runtime, not precomputed into candidates, so their duplication/overlays alone do not block a quirk. Missing or unresolved same-priority `max_hp` Buffs do block writing. Known flat/percentage HP effects use `(selected armor HP + total flat modifiers) × (1 + total percentage modifiers)`. `always` and `no_trinkets` apply to a new unequipped candidate; `afflicted`, `in_mode`, and `lightabove` remain runtime-conditional. The editor checks reachable combinations of known conditions and rejects selections that could produce a non-positive HP base or multiplier. Quirk Buffs are not copied into `actor.buff_group`, preventing duplicate runtime application.
- Combat skills are sampled without replacement. When `generation_guaranteed` marks exist, at least one marked skill is selected, not necessarily all. The equipped target is the smaller of the generation count and selection limit; short pools yield fewer skills with a warning. Skill maps retain native zero values, while personal purchases in `persist.upgrades.json` express levels and unlocks. Damage, accuracy, effects, and other class combat attributes are resolved by the game from effective definitions rather than copied into saves. Shared/class camping pools are sampled independently without filling a shortage from the other pool; all recognized available camping skills are unlocked regardless of which are equipped. See [Hero Skins and Initial Skill Selection](docs/hero-generation-selection.md).
- Hero preview changes temporary `persist.town.json`, `persist.roster.json`, and `persist.upgrades.json`. A candidate with `shard_hungry` goes to the shard stagecoach; others go to the ordinary stagecoach. Preview advances `nextGuid` and appends level-appropriate personal purchases for the same GUID. Preview and confirmation show the actual target pool. Semantic catalog fingerprints are rebuilt before/after preview and during commit; active Mod/DLC, manifest, class, quirk, level-threshold, or upgrade-template changes reject an old preview. All three files must pass full DSON round-trip equality before confirmation. Commit order is upgrades, roster, then town. Any failure rolls back every replaced file from the complete backup, whose manifest records candidate XP, equipment ranks, and purchase count.

The main window and quirk picker share Darkest Dungeon-style panels, dark/red native window frames, and a full-window charcoal texture visible through translucent panels. Presentation does not change the preview → confirmation → backup → commit workflow. Encoding is followed by another decode to verify target quantities, profile summaries, and DSON revision fields. Real saves are replaced only after explicit confirmation, a closed-game check, unchanged source hashes, and a backup of all profile `persist*.json` files.

## Write and recovery boundaries

1. **Generate safe preview** copies, decodes, edits, and encodes only temporary workspace files.
2. Apply is rejected if a source-save hash changes after preview.
3. **Apply to save** checks that `Darkest.exe` is not running.
4. Before writing, a complete timestamped backup and manifest are created under `%LOCALAPPDATA%\DarkestDungeonSaveEditor\backups`.
5. If replacement or final hash validation fails, the editor attempts immediate recovery from the backup.

Hero creation only appends new stagecoach candidates: `shard_hungry` selects the shard pool, otherwise the ordinary pool. It does not modify owned heroes, stagecoach draw history, week count, blacksmith upgrades, quests, town-event history, or game-content files. Higher-level candidates receive personal XP, equipment ranks, and skill/equipment purchase chains without unlocking town buildings such as the blacksmith or guild. Return-from-the-grave events remain a separate future feature requiring native save-difference evidence.

Each launch creates `logs/app-<date>-<time>-<milliseconds>-<process-id>-<random-id>.log`. Stages, exceptions, UI status, and full catalog diagnostics stay in that session's file, including after midnight. Earlier daily/session logs are preserved. Startup records the current log's full path. After loading, the lower log area shows profile/mode/source summaries and context-specific counts for items, hidden definitions, inventory slots, trinkets, heroes, quirks, names, and levels. Occupied raid slots count every saved entry, including carried trinkets excluded from the quantity-item catalog. These summaries do not crowd the catalog controls. Persistent logs include the full profile path, SHA-256 of `persist.game.json` and the current quantity-source save, and the estate-save hash in raid mode. Development runs locate `DarkestDungeonSaveEditor.sln` above the program directory and use the repository's `logs`; standalone builds without that solution use `logs` beside the EXE. Each load combines main-catalog, encounter, and attachment diagnostics by file/cause while retaining reporting modules. Reloads record them again. The UI shows at most 30 grouped diagnostics; the file retains all. Workspaces and save backups remain under `%LOCALAPPDATA%\DarkestDungeonSaveEditor`.

Automated editor checks use isolated fixtures or read-only save analysis. Real-game verification requires an explicitly selected target, full backups, hashes, and captured evidence; historical test profiles do not authorize future writes. A new campaign requires a confirmed empty slot and must not overwrite an existing profile. The game may also update shared `profile_9` data, so a temporary campaign does not isolate the entire user-data directory. Developer-specific profile assignments, review reports, and experiment procedures belong in the ignored local history directory. Reference projects and experimental saves from `DarkestDungeonRuntimeFramework` can supply read-only evidence and fixtures, but its custom plugin priority is not the game's native Mod order.

Hero generation does not require an owned instance of the selected class. Active `.info.darkest` files supply generation, skill, and equipment rules; the generic save structure comes from real stagecoach candidates. Some Mods disable random quirks and later grant special ones through effects that assign `disease`, or through town events. Catalog discovery scans actual assignment effects; unrelated combat effects do not produce irrelevant conflict diagnostics.

Items, heroes, quirks, trinkets, monsters, and curios share English/Simplified Chinese name loading from valid `.string_table.xml`, legacy `.loc`, and `.loc2` files. Within one source, nonempty names use `.loc2 > .loc > XML` priority independently for each language, preserving Mod order. Missing languages remain empty. Mod localization is manifest-gated: unlisted XML is not read as a fallback, and malformed XML is not repaired. Missing manifests are prepared only during explicit loading. LOC/LOC2 reads only direct English/Simplified Chinese files under the corresponding `localization` root, without recursively scanning platform or old directories. `.unused` files are excluded; nested XML rules are documented under [Localization](docs/content-save-rules.md#3-localization).

LOC and LOC2 use their respective table layouts. Invalid headers, indexes, offsets, lengths, or NUL boundaries reject the whole table. An individually bounded entry with invalid UTF-8 or compiled color codes is skipped while valid names remain; diagnostics summarize the file's skipped count and up to three examples without guessing encodings or inserting garbled text. Compiled color start/end markers may span strings. XML must first pass strict parsing; invalid individual entries with missing IDs/language IDs or ambiguous nesting can then be skipped. Broken encoding, tags, or CDATA reject the whole file. Fallback uses only legitimate same-language sources, never unlisted files. An unreadable manifest or invalid path stops that catalog request. The `JoanofArc` name is read directly as `Ruler` from its two listed LOC files. Random hero names still come only from valid XML. Synchronization and pre-write checks never silently generate manifests.

Missing continuous equipment ranks, upgrade codes, or valid HP can leave a proven level-0 template usable while unsupported higher levels remain unavailable. Explicit `singleton` and positive `roster_limit` quirks remain writable under their distinct warning/recruitment rules. Missing/unresolved HP Buffs or unknown conditional HP rules block selection. Structurally complete evolution settings with valid durations are supported; unknown or invalid settings remain blocked.

`actor.buff_group_next_guid=2` is the smallest value observed in a real saved stagecoach candidate. It does not participate in HP calculation, and `buff_group` remains empty. A historical DSON/live-game check added a base Hellion named `Cumin`, GUID 364, to the ordinary stagecoach after a full backup. The game displayed that candidate while the owned roster remained at 36 heroes. The candidate saved `current_hp=23.4` from base HP 26 and `fragile` at -10%; the UI displayed maximum HP 24 with the base/quirk breakdown, confirming no duplicate quirk application. Normal load and exit did not rewrite `persist.town.json` or `persist.roster.json`, so that check does not prove reserialized `buff_group_next_guid`/`buff_group` values or the result after recruitment into the roster.
