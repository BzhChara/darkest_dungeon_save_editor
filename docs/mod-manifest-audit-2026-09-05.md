# Mod 清单差异审计 — 2026-09-05

后续更新：用户确认“怪物属性修改”为其数值生成脚本，并于同日晚授权按保存配置完整重跑。原版生成文件中缺失燃烧死亡判定的两份已更新；另处理了 31 个工坊怪物 Mod 和 1 个本地 Mod。详见 [运行与验证记录](monster-stat-refresh-2026-09-05.md)。本文以下数量和哈希描述保留为**重跑之前的审计快照**，不代表重跑之后的文件状态；编辑器读取规则仍未改变。

## 结论

“统一发现实际文件，再与清单比对并分析差异”有实际价值。本次确实找到了清单外文件，但它们不能统称为漏读或旧文件：259 份当前编辑器内容目录范围内的候选，分别是 **1 份已经补读的译文、8 份与当前本机原版逐字节相同的文件、250 份修改后的怪物定义**。

本轮只审计并记录结果，没有改变编辑器的目录纳入规则，没有修改、移动或删除任何 Mod/存档文件，也没有运行 Mod 自带脚本。下述“编辑器未读取”不等于“已证明游戏不读取”；本次没有验证游戏引擎对清单外文件的实际加载行为。

## 三、250 份脚本生成的怪物覆盖文件

`Monster attribute(怪物属性修改)`（`3705402044`，此次仅在 `profile_1` 启用）的清单只有说明、脚本、图标和 `project.xml` 等 5 项，没有列入 `monsters` 下的 250 份 `.info.darkest`。

该 Mod 的说明文件及 `auto_balance.py` 源码表明：这些路径是把本体怪物定义调整后写入此 Mod 的输出位置。本轮只阅读它们，没有运行脚本。

### 文件内容证据

- 250 个怪物 ID 均有原版同路径定义，不是 250 个新增怪物。
- 250 份文件全部与原版不同。
- 248 份在规范化换行后，除了 `stats:` 行以外完全一致。
- 例如 `brigand_cutthroat_A`：原版 HP 12、SPD 3、PROT 0.15；清单外文件为 HP 18、SPD 5、PROT 0.30。
- 另两份 `ancestor_big_D`、`ancestor_pod_D` 除属性外，还在 `death_class:` 中缺少当前原版的 `.is_valid_on_burn_dot True`。这是需要核查旧版本基底的具体证据，不能把所有生成文件都假定为与当前原版同步；也不能仅凭这一处差异断言作者无意删除该字段。

### 引用与影响边界

现有有效引用文件中可以找到这些 ID，例如：

- `brigand_cutthroat_A`：官方庭院 `courtyard.2.mash.darkest` 的命名遭遇，以及农场波次遭遇表。
- `ancestor_big_D`：当前有效水月怪物定义中的 `death_class` 转换，以及 AI 定义。

这能证明相关怪物仍在当前内容中使用，但不能证明游戏读取的是哪一份同 ID 文件。`profile_1` 中水月怪物强化的优先级还高于这个属性修改 Mod，最终覆盖关系也必须计算。

当前编辑器的怪物目录主要读取 ID 和 Boss 标记，并不向存档写入怪物 HP、伤害等完整属性。本组文件没有新增 ID，比较发现的差异也没有改变 Boss 标签。因此不能将“未纳入这 250 份属性覆盖”描述成“编辑器漏掉了 250 个可生成怪物”，更不能据此声称游戏内属性修改已验证有效。

结论是：**用途有证据的生成覆盖候选，其中 2 份存在旧基底风险；是否应纳入有效目录仍待核实游戏加载规则。**

## 四、无清单 Mod 的重复分析

14 个无清单 Mod 共检查了 1,336 份内容目录候选文件。这里包括 `.art.darkest` 和 `.loc/.loc2` 等配置/本地化资源，不代表 1,336 个可生成物品或人物。

发现 128 组“同一 Mod 内字节完全相同的文件”，以及水月 Mod 中 45 份与原版同路径相同的文件。但这些不能直接变成去重或清理名单。例如：

1. 水月的 `dungeons/cove/cove.conditional.3.mash.darkest` 与对应遗迹、兽窟、荒野表字节相同，路径却指定不同地区。按内容哈希去掉其中几份，会丢失地区范围。
2. 红莲和 The Wild Hunt 的多个语言 `.loc2` 内容相同，但文件名区分语言。编辑器只选择简中、英文，不代表可以删除其他语言文件。
3. 秘术师的多个怪物 `.art.darkest` 文件相同，但属于不同怪物路径，不能仅凭相同内容认定废弃。

因此需要修正讨论中的一句过于宽泛的建议：“内容完全相同就不重复加入目录”。只有在**资源身份、有效路径/地区/语言/难度等作用范围也相同**时，才可以考虑合并处理；不能跨路径只凭哈希去重。

名称含 backup/old 的提示也不能作为旧文件结论。此次无清单来源的名称提示命中是脚本备份元数据，不是可删除的业务定义。

## 五、对后续统一扫描实现的建议（尚未实施）

1. 所有已启用来源先做文件清点；清单是比对信息，不应导致清单外文件完全没有诊断记录。
2. 把“清单内且存在”“清单缺失项”“清单外”“无清单”分开记录；再区分编辑器已补读、内容不同、内容相同但作用范围不同、待核查等结果。
3. 数据、显示文案、资源、工具/元数据按各自规则分析。不要把不属于编辑器功能范围的文件判成无效 Mod 文件。
4. 精确引用只能作为一项证据：同 ID 可以有多份定义；零命中也可能是分析范围有限，不能用它自动判旧。
5. 保留清单外候选与最终有效目录之间的边界。在运行时加载语义未确认前，不因“路径合法且有引用”直接提升为可写内容，不修改清单，不清理用户文件。
6. 先针对本次实际候选确认规则，再实现自动补读；这轮没有新增长期后台扫描或新的 UI 警告。
