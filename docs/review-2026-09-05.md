## 1. 优先处理的功能问题

以下 R1–R5 是修复前的审查证据；当前进展见 [修复记录](review-fixes-2026-09-05.md)，不应把历史复现结果当作新版运行结果。

### R1 / P2：无清单 Mod 的 DLC 子目录会漏扫

有 `modfiles.txt` 时，目录扫描会接受已启用的 `dlc/...` 虚拟路径；没有清单时，人物、饰品、物品和遭遇的回退扫描只从 Mod 顶层标准目录开始。这两个分支对同一套有效内容的处理不一致。

隔离复现：复制契约夹具中的启用 Mod，保持所有文件相同，仅在副本中不提供清单：

| 对象 | 有清单 | 无清单 |
| --- | --- | --- |
| `dlc_shared_trinket` | Mod 覆盖，价格 8800 | 退回 DLC 定义，价格 2000 |
| `enabled_dlc_trinket` | Mod 覆盖，价格 8200 | 退回 DLC 定义，价格 2000 |
| `dlc_shared_hero` | `modded_dlc_skill` | 退回 `shared_dlc_skill` |
| `enabled_dlc_hero` | `modded_enabled_dlc_skill` | 退回 `enabled_dlc_skill` |

风险是漏掉新增内容或使用错误的下层模板，不只是少一条来源说明。当前真实扫描没有找到满足本探针条件的无清单 DLC 子目录实例，因此这是已复现的兼容性缺陷，不应描述为所有现有本地 Mod 都漏扫。

定位：[人物发现](../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.SourceDiscovery.cs)、[饰品发现](../src/DarkestDungeonSaveEditor.Core/TrinketCatalog.cs)、[物品发现](../src/DarkestDungeonSaveEditor.Core/QuantityItemCatalog.SourceDiscovery.cs)、[遭遇发现](../src/DarkestDungeonSaveEditor.Core/BattleEncounterCatalog.SourceDiscovery.cs)。建议统一“顶层标准目录 + 已启用 DLC 根”的发现规则，继续排除未启用 DLC 和残余目录。

### R2 / P2：物品场景仅以副本文件存在与否判断

`QuantityItemCatalog.LoadAsync` 和提交前的 `ValidateQuantityItemSaveContext` 都只检查 `persist.raid.json` 是否存在，没有结合 `persist.game.json` 的 `inraid` / `raiddungeon`。

隔离复现：`inraid=false`、`raiddungeon=none`，同时保留有效的旧副本文件，目录仍返回 `SaveContext=Raid`。强制回城功能本来就只改游戏入口、保留地图和副本文件，因此这也是项目自身能够产生的过渡状态。

影响：回城状态下仍可能显示旧背包目录，让用户修改无效的残留背包，同时无法使用小镇物品；写入前的相同判断不会纠正它。不能据此声称已经发生坏档。

定位：[QuantityItemCatalog.cs](../src/DarkestDungeonSaveEditor.Core/QuantityItemCatalog.cs)、[SaveEditService.QuantityItems.cs](../src/DarkestDungeonSaveEditor.Core/SaveEditService.QuantityItems.cs)。建议统一场景解析，并将“已请求回城，等待游戏完成清理”与正常小镇/副本区分开。

### R3 / P2：人物可生成状态没有覆盖完整生成条件

实际调用当前生成器，不写文件：

| 档案目录快照 | 人物定义 | 0–6 级组合尝试 | 成功 | 被拦截 |
| --- | ---: | ---: | ---: | ---: |
| `profile_0` | 44 | 308 | 294 | 14 |
| `profile_1` | 51 | 357 | 329 | 28 |

`profile_1` 的四个职业在全部七个等级都被拦截：

- `EosNyx`：缺少 `EosNyx.EosNyx_SK8` 的购买升级树；
- `Kaltsit`：缺少 `Kaltsit.Kaltsit_Ranged_8` 的购买升级树；
- `HMSTerror`：缺少 `HMSTerror_SK4/5/6` 的购买升级树；
- `Doombringer`：生成模板要求 2 个职业露营技能，实际有效目录只有 1 个。

这些定义的 `ProgressionUnsupportedReason` 都为空、装备等级资料完整，界面因此显示“0-6级完整”和手动生成能力，但最终生成器使用了更严格的检查。明确缺陷是目录/可用性提示与实际能力不一致。特殊多形态技能是否需要独立购买树、是否应放宽生成策略，还需要针对这些定义确定规则；不能未经验证一律删掉检查。

原始文件也有对应证据：`EosNyx_SK8` 在角色 info 中声明了多级形态技能，但没有相应升级树；Doombringer 的 camping 文件只声明 `Doombringer_1`。不能把所有拦截都解释成解析器丢了文件。

定位：[HeroRow.LevelSummary](../src/DarkestDungeonSaveEditor.App/MainWindow.RowModels.cs)、[升级购买检查](../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs)、[候选生成器](../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.cs)。建议目录提供与预览共享的完整可生成性结果，随后单独处理特殊技能模型。

### R4 / P2：人物与饰品不能按显示出来的来源搜索

物品筛选包含 `SourceLabel`，人物和饰品只搜索内部 `Source`。显示为“原版（当前由某 Mod 覆盖）”时，内部值可能是 `workshop:...`。

`profile_1` 的实际目录中，15 个人物、490 件饰品显示为原版来源；按现有谓词搜索“原版”时，两者均得到 0 条。按 Workshop Mod 的显示名称搜索也有相同风险。

定位：[MainWindow.CatalogInteraction.cs](../src/DarkestDungeonSaveEditor.App/MainWindow.CatalogInteraction.cs)。建议与物品页一致，同时匹配内部来源和显示来源。

### R5 / P2：Bridge 的零权重会污染普通战斗分类

`ClassifyEncounter` 把非正权重的标准 hall/room 行标成 `ConditionalOrAdditional`。托管 Bridge 的追加行也使用 `.chance 0`，目的是不参与自然随机生成，不代表它原本就是特殊遭遇。

隔离复现：遗迹中的正权重普通组合，在海湾 Bridge 中以零权重复制后，同一组合被解析为 `Ordinary` 和 `ConditionalOrAdditional` 两种类别。界面随后按完整敌方 ID 组合合并，并优先保留特殊分类，再过滤“普通战斗”，于是原本的普通组合可以从普通列表消失、进入特殊列表。

这是隔离复现与当前 UI 合并逻辑共同支持的结论；当前真实 Bridge 快照没有找到“普通来源 + 托管零权重来源”的混合组，不应声称已经在该快照发生。

定位：[ClassifyEncounter](../src/DarkestDungeonSaveEditor.Core/BattleEncounterCatalog.cs)、[GetEncounterPickerCandidates](../src/DarkestDungeonSaveEditor.App/BattleMapView.Commands.cs)。建议保留托管条目的原始来源分类，不能从载体权重反推玩法类别。
