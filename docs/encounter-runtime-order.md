# Native encounter ordering (2026-09-06)

The editor supports multiple standard mash files from the game's root `dungeons` tree, enabled root-level Mods, and one contributing DLC mount per region/difficulty. Each `hall`, `room`, and `boss` table has its own zero-based runtime index. A source line number or file-local row ordinal cannot substitute for that index.

## Evidence and scope

Read-only disassembly of the installed Windows x64 build 27890 established the following behavior. The executable SHA-256 is `35E5A653279992564809FF8406FEBD5A02A7D6961044781B1296B38A7096F59B`, image base `0x140000000`. Addresses below are virtual addresses in that executable. No game process or original content was modified to obtain this evidence.

| Native code | Observed behavior |
| --- | --- |
| `0x1404C90F0` (MashGuide loader), query at `0x1404C9239` | Searches `dungeons/<dungeon>/` recursively with the standard `<dungeon>.<difficulty>.mash.darkest` suffix. Consumes returned files forward, then their lines in order. Conditional and additional collections are separate. |
| `0x140247D20` (`IO_FindFiles`) | Enumerates the base device first, then alternate mounts in reverse registration order. This call uses flags 0, so no final reversal or erase-and-reappend override occurs. |
| `0x1403EBB50`, registration call `0x1403EBF68`; mount append `0x140238430` | Enabled Mods register in profile order. Reverse enumeration applies lower-priority Mods before higher-priority Mods. |
| Startup calls `0x1403D6BAC` and `0x1403D6BC7`; DLC registration `0x1403EC920` | Mods register before DLC. Reverse enumeration consequently applies DLC mounts before root Mod mounts. The order between multiple DLC feature/package mounts is not generalized by this implementation. |
| `0x140247970`, especially `0x140247C5E` and `0x140247CA5` | A later matching relative path replaces the existing result in place. A distinct path appends. A base or lower-priority file therefore establishes a slot even if a later Mod supplies its final bytes. |
| `0x140247B9C`–`0x140247BDC`, matching at `0x140247C00`–`0x140247C2D` | Matching strips the alternate mount prefix. A root Mod's `dungeons/x/file` can replace `dlc/<enabled-prefix>/dungeons/x/file` in the original slot. Authored paths remain distinct for source lookup and Bridge output. |
| `0x140374460` (Windows device), sort `0x140374E28`; manifest enumeration `0x1402396F0`, sort `0x14023A018` | Both physical-directory and manifest-backed enumeration sort deeper paths first, then case-sensitive `strcmp` order. Manifest line order does not determine runtime mash indexes. |
| `0x1404CA033`–`0x1404CA2DF`; last-substring helper `0x14036B300` | Parsing starts after the last `.types` substring and copies four actor slots. Repeated `.types` and a glued `0.7.types` field therefore remain readable. Fifth and later IDs are ignored. |
| `0x1404C9EE0`–`0x1404C9F57`, `strtod` call `0x1404C9F35` | `.chance` reads a numeric prefix after the last recognized field; NUL/end, TAB, SPACE and `=` are qualifying key boundaries. A final empty field overrides an earlier value with zero. `0x1404C9F3E` converts to float before float percent scaling; `1e-50` becomes zero. A following `.types` does not invalidate `0.7`. Zero weight affects ordinary filtering but does not delete the runtime slot. |
| `0x1404CB740` (`AddMashEntry`), check `0x1404CB909` | Resolves four actor slots, sums their monster sizes, and appends only when the total is at most four. Missing definitions contribute zero size and do not remove the row. |
| `0x1404CDA30`, last-field call `0x1404CDAA4`, assignment `0x1404CDABD` | Monster `display: .size` uses the last field and native integer-prefix conversion. A quoted numeric value becomes zero. Actor construction initializes size to zero (`0x1404804D0`); later canonical info/art declarations can replace it. Overflow, negative values and unsupported byte-truncated IDs remain guarded. |
| `0x1404CD210` | Discover monster IDs from enumerated info filenames, remove the final two bytes for the family, then open `monsters/<family>/<id>/<id>.info.darkest` followed by `.art.darkest`. The enumerated file itself may be a decoy; its size/tags must not be used as the class definition. |

Red Hook's [official guide](https://steamcommunity.com/sharedfiles/filedetails/?id=819597757) independently documents profile Mod priority and same-path replacement. It does **not** specify multi-file enumeration order; the native code above is the ordering evidence.

DLC tables and root Mod overlays are now reconciled by mounted relative path, so a shadowed built-in table is not counted twice. A region/difficulty whose indexed declarations span multiple DLC prefixes still stays guarded. Files containing only `named`, `stall`, or other non-indexed declarations do not trigger that restriction. New DLC-relative files supplied only by a Mod, without an existing built-in provider, can be Bridge formation sources but cannot establish a proven destination index; native discovery for that case has not been established. Nonstandard directories and case-only path collisions also stay guarded. The native evidence is scoped to this Windows build; it is not a claim of testing every executable/platform or future engine version.

## Resolver contract

1. Resolve active same-path overlays while retaining their full provider chains.
2. Replay every root provider at its own application position, original path depth, and original case-sensitive filename. The first appearance establishes the slot; later applications can change its content without moving it. DLC-prefixed paths keep their DLC mount position even when a Mod supplies replacement bytes. A root Mod must still be replayed after DLC even if Base already established the root path's slot.
3. Reconcile DLC/root aliases using mount-relative paths, replacing an existing slot in place and retaining the full provider chain. Parse effective files in that order and assign independent `hall=0`, `room=1`, `boss=2` counters. These are case-sensitive declaration kinds. The common native record reader consumes logical declarations, including multiple declarations on one physical line or one declaration spanning lines; slash comments, hash boundary comments, NUL termination and invalid-current-header termination apply. `SourceLine` is a display location; `SourceRecordIndex` distinguishes declarations in the same file and participates in source identity, classification and preflight checks. Neither is a runtime mash index.
4. Read the last `.types` field and count raw slots before removing empty quoted actors from the displayed formation: `a "" b c d` consumes four native slots as `a, empty, b, c` and ignores `d`. Each slot retains at most 31 UTF-8 bytes. Dot-prefixed tokens are ordinary monster IDs, not field terminators. Apply truncation before resolving definitions and sizes; an incomplete UTF-8 prefix makes the affected type unproven. Explicit all-empty actors and unresolved monsters keep their index slots but cannot be written. A known total size over four skips that row without consuming an index, preserving later usable rows. A genuinely unparsed declaration, missing `.types` value or unknown size still withholds the affected type rather than guessing later indexes. Roaming classification uses the last exact `.random_dungeon_roaming_id`, up to 63 bytes; an explicit empty value clears it.
5. Fingerprint the ordered effective inventory and winning bytes, and recheck the profile configuration and monster definitions before writing. Adding a shadowed lower-priority provider can move a slot even when every winning file is byte-identical; ordered inventory comparison must catch it.

For example, Base provides `cove.2`; a lower-priority Mod adds `a.cove.2` and `z.cove.2`; a higher-priority Mod overrides `cove.2` and adds `0.cove.2`. The runtime file order is `cove.2, a.cove.2, z.cove.2, 0.cove.2`. The override remains in the Base slot, and the new `0` path remains after the lower-priority Mod's additions.

## Bridge contract

Both managed installation and probe generation use `BattleEncounterCatalog.ResolveAppendTarget`. A profile package stores only generated rows in `dungeons/<region>/ddse_managed.<region>.<difficulty>.mash.darkest`, shared by all three types for that destination. Original Base/DLC/Mod files are not copied or overridden. A unique root-level path is appended by the highest-priority managed mount; a filename prefix alone does not establish order. Any other provider of that path, including a shadowed provider or DLC alias, is rejected. An existing dedicated file must remain the final contributor for the selected type.

The next global index counts native retained rows across all effective files, excluding known oversized rows and retaining missing-definition slots. An absent type can start at index zero after complete parsing proves it empty; no copied carrier is needed. Version-4 manifests require both the runtime/global `MashIndex` and the file-local, per-type `FileRowIndex`. The two numbers must never substitute for each other. Version-3 copied-file packages require explicit cleanup before installing version 4; reading a package neither migrates it nor deletes files or saved battles.

Before installing a staged package or activating it in the profile, resolve the staged content and require all previously addressable type/index pairs to retain their original composition, virtual source path, and source line. Verify every managed entry against both its local ordinal and global index. A historical entry with a missing monster can retain its slot without blocking another valid entry; the historical entry itself remains unavailable for placement. A changed or removed slot still fails verification. Repeat those checks after installation. A stale offset, changed earlier table, invalid manifest, or reactivation that changes existing bindings fails before map placement; transaction recovery preserves newer external save data.

Generated rows place all options before `.types`, for example `hall: .chance 0 .limit 1 .can_be_ambush false .types bandit_A`. Appending options after a short monster list would put those option tokens into the remaining native actor slots. Installation, maintenance rebuilding and diagnostic probe generation share this formatter. Classification manifests additionally record the original source declaration ordinal; source verification includes that ordinal, not just its physical line.

Bridge definitions persist per destination region, difficulty, and type. For a table containing indexes 0–10, a new formation appends as 11; an existing matching ordered formation is reused. The map stores that type/index binding. Generating another region retains prior region tables, and deleting a map battle does not delete its Bridge definition. Returning to a region can reuse the previous entry if the enabled content and managed package still validate. Generated rows use `.chance 0`; hall/room rows also use `.limit 1 .can_be_ambush false`. A newly generated map does not automatically place earlier battles, and monster IDs/assets continue to come from their original active content.

Adding a Mod can move an existing Bridge row from global index 10 to 11 without changing the dedicated file or its local ordinal. A saved map cell containing 10 remains 10: game table construction is not a saved-reference migration. Before app map writes, and during profile synchronization, the editor now reconciles its own records as described below. Low-level append validation still rejects stale manifests until reconciliation succeeds.

## Automatic editor battle maintenance (2026-09-07)

The confirmed policy is to clear all still-present battles placed by the editor in the current raid when a recorded type/index no longer resolves to its original usable ordered formation, or a managed Bridge formation is removed/reindexed. Direct local placements and Bridge placements are both tracked. Native game-generated battles are outside the editor's responsibility and are neither renumbered nor cleared. Merely changing file bytes, names/descriptions or combat stats without changing a recorded binding/availability does not clear battles.

Successful map backups and their complete `commit-result.json` markers serve as the placement journal. New backups include `RaidIdentity`; pre-feature records can be read only when their verified map/raid backups establish the same identity. The identity includes the raid start timestamp, quest identity and stable map topology, excluding mutable exploration and attachments. Failed preparations/backups do not establish ownership. Explicit content deletion/replacement retires a cell; a cleanup completion retires the preceding journal. The current cell must still contain a battle with the recorded type/index. Corrupt provenance or an unidentifiable raid causes deferral instead of guessing from numeric IDs.

Before invalidating records or compacting the package, inspect current battles for old Bridge type/index bindings without a matching successful placement record in this raid. Such a cell could be an old Bridge reference or a native battle in a later raid; neither ownership can be inferred from its number. Defer the transaction, preserve both map and package, and report that the placement records must be restored or the raid exited first. This also guards completely missing or partially lost history. Deleted history cannot reconstruct the ownership of direct local placements, so the successful backup records must be retained.

Confirmed missing monsters and formations known to exceed four slots are removed from the current profile's version-4 Bridge. Retained rows receive new per-type local ordinals and global indexes after resolving the staged overlay against current Base/DLC/Mod data. Empty dedicated files may remain but contain no removed rows. Valid source/order fingerprint changes that leave all recorded bindings intact only refresh metadata. An enabled local Mod that cannot be mapped by its project title is incomplete source resolution, not evidence that its monsters were deleted. Existing version-3 packages remain unsupported; this is not a legacy package migration.

Since 2026-09-10, maintenance also retires a version-4 entry whose old generated options occupy monster slots and therefore disagree with its manifest composition. This exception requires the package's validated hash **and** exact reconstruction of the prior generator's entire file text, with matching per-type record counts and ordinals. Unrecognized edits still defer. The same current-raid ownership checks apply before any removal, compaction or map write. An affected owned entry triggers the existing policy to clear all still-present editor battles, including direct placements; a correct four-monster row can remain. This does not make old option tokens invisible to the parser or provide a general old-format compatibility layer.

Maintenance preserves the current Mod order. The existing append requirement still applies: the Bridge file must be the final contributor for the selected type. If a newly added higher-priority Mod places another contributor after it, restore the managed Bridge to highest priority before appending; maintenance does not automatically reorder other Mods or rewrite the profile's enabled-Mod configuration.

Only battle content and `mash_index`/`mash_type` are cleared on owned cells. Guarded curios/treasures become unguarded curios/treasures; their prop bindings, all other map content, topology, party position and exploration remain intact. The policy clears editor replacements instead of restoring the original fight that the editor replaced.

The shared profile reader is still read-only. A 10-second application poll resolves content sources and hashes encounter files, monster info files and Mod inventories even when no save file changes. Profile loading starts the same synchronization path. Map actions repeat maintenance with freshly resolved content before preparing a write. A maintenance change refreshes the map and requires selection from the updated map. Game-running detection defers all live save/package changes and automatically retries after exit. Unproven encounter tables or incomplete source discovery defer maintenance and map writes; they do not disable inventory/hero synchronization. Logs report removal/reindex/clear counts, reasons and the backup directory, with repeated deferrals deduplicated.

Every applied maintenance transaction backs up all profile saves and the managed package, checks DSON roundtrips/revisions, guards file hashes and keeps replacements locked through the completion marker. Map placement and maintenance publish completion markers by flushing a temporary file and renaming it; only a complete marker matching the profile, target and backup is accepted. Failures recover exact displaced bytes while preserving newer external versions. A pending transaction with a missing, truncated or incomplete marker can recover on the next service instance only when the game/raid and all affected target files still match the recorded before/after hashes; otherwise it stops with the backup location. A recovered cleanup record does not retire placement history. Generated staging files are disposable and removed after each check; polling does not create permanent staging archives.

`EncounterMaintenanceContractTests.cs` covers direct/Bridge cleanup together, native and attachment preservation, old backup provenance, completely/partially lost records, repeated fixed maps in new raids, ambiguous old numeric bindings, deletion/reindex/reuse, unmapped enabled local Mods, game-running deferral, incomplete-table rejection, stats-only updates, DSON revisions, group rollback, interrupted recovery with missing/truncated/incomplete markers and external-write preservation. `ProfileSyncContractTests.cs` also verifies a Mod encounter update is detected without any changed profile save hashes.

## Validation boundary

`MultiFileEncounterContractTests.cs` covers first-provider slots, two Mod priorities, depth order, misleading manifest order, shadowed-provider changes, native four-slot normalization, invalid row guards, all three Bridge types, the shared dedicated file, duplicate reuse, and DSON map create/replace/delete. `DedicatedBridgeContractTests.cs` covers unavailable historical units, zero-weight rows, path collisions, tail guards, changed Mod indexes with unchanged saved references, and explicit manifest version boundaries. Existing contracts cover single-file DLC, classification metadata, saved-state guards, and replacement races.

`DlcNativeEncounterContractTests.cs` covers DLC/root alias replacement with and without an existing Base path, unrelated named-only DLC files, repeated/glued fields, oversized and missing-definition slots, all three managed Bridge types, DSON map writes/deletion, and region round-trip retention. Multi-file tests cover repeated monster sizes and stale-index rejection after a size change. Manifest-free discovery tests keep Mod-only DLC additions available as formation sources while guarding their unverified native target discovery.

The initial multi-file verification of copied `profile_1` saves resolved 65 hallway, 69 room, and 4 boss indexes for weald difficulty 1. A later user-generated Bridge entry extended the boss table to five rows. These are destination table counts, not a count of all selectable bosses. Copied-profile catalog checks and staged packages establish editor addressability for their content snapshot; they do not constitute an in-game combat/reload test or install test packages into the user's game.

### Runtime row-occupancy experiment (2026-09-08)

An authorized temporary Mod appended nine zero-weight hallway rows to the actual `profile_1` weald/1 content. Read-only capture after entering that expedition found eight retained rows at indexes 65–72: a missing-only row retained 66, a mixed valid/missing row retained 67, the size-5 row was omitted, an all-empty `.types ""` row retained 69, and a size-0 definition retained 70. A fifth raw actor was ignored even when its size would have made the row oversized. Room/boss table counts remained 69/4.

The editor at the time of the experiment withheld hallway indexes because of the all-empty row; it did not silently skip it and write shifted indexes. Since 2026-09-09, explicit empty rows retain non-placeable slots across direct validation, Bridge append and maintenance. `EmptyEncounterSlotContractTests.cs` covers all three supported types, later normal rows, missing/oversized actors, ignored fifth actors, forged empty-row writes, Bridge append, map create/replace/delete and unchanged maintenance. Missing `.types` declarations remain guarded. The original experiment establishes native table occupancy, not successful combat with null or size-zero actors. No test battle was placed in the real saved map. See the [measured matrix](resource-duplicate-semantics.md#5-index-occupancy-of-invalid-encounter-rows), [original experiment](change-history/resource-semantics-live-2026-09-08.md) and [integration record](change-history/resource-semantics-integration-2026-09-09.md).
