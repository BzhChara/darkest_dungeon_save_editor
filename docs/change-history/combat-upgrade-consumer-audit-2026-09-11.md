## 1. P2：战斗技能仍以完整拼接字符串绑定升级树并写入购买编号

### 触发与影响

当 `<职业 ID>.<战斗技能 ID>` 超过 63 个 UTF-8 字节时，游戏构造的查询目标与编辑器不同。样例中的职业 ID 为 `audit`，技能 ID 本身均未超过 63 字节，也没有 NUL、截断的半个 UTF-8 字符或哈希碰撞。

| 组合 | 拼接长度 | 编辑器当前行为 | 原生查询合同对应结果 |
| --- | --- | --- | --- |
| `audit.` + 57 个 `a` | 63 字节 | 写入完整目标的 `0/1` | 正常读到第 1 档 |
| `audit.` + 58 个 `a` | 64 字节 | 写入完整 64 字节目标的 `0/1` | 查询的是前 63 字节目标，找不到这些购买项 |
| `audit.` + 19 个“营” | 63 字节 | 写入完整目标的 `0/1` | 正常读到第 1 档 |
| `audit.` + 20 个“营” | 66 字节 | 写入完整 66 字节目标的 `0/1` | 同样查询前 63 字节目标，找不到这些购买项 |

这里“第 0 档”是技能 1 级，“第 1 档”是技能 2 级。返回 `-1` 表示此查询没有找到基础解锁。

问题横跨两个入口：

- [目录绑定](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.Progression.cs#L101)直接用完整 `<class>.<skill>` 查找树。若 Mod 已按原生目标编写 63 字节树名，编辑器会漏绑它，误走“无购买升级树”分支。若完整树和截断树都存在，编辑器还会选择不同的树：本轮对照中完整树的第二档门槛为 1，原生查询目标对应树的门槛为 3，编辑器采用前者。
- [生成购买项](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs#L29)继续用完整字符串；[隐式技能补齐](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.ImplicitSkills.cs#L39)也沿用传入的完整目标。现有树和无树两条路径均可写错购买 hash。无树样例虽然提示“仅做基础解锁”，实际保存目标也不能满足原生基础解锁查询。

目录可生成预检、候选生成和保存写入均接受这些隔离样例。保存器正确保存了传入的完整目标 hash；错误在它之前形成，不能靠 DSON 往返自行修正。

### 原生证据

只读核对本地 x64 build 27890 `Darkest.exe`，SHA-256：

`35E5A653279992564809FF8406FEBD5A02A7D6961044781B1296B38A7096F59B`

- `0x1405C718F`–`0x1405C71AE`：普通战斗技能等级更新分支以 `%s.%s` 构造职业／技能目标，调用 `0x14036B3A0`。
- `0x14036B3CB`–`0x14036B3F2`：格式化容量为 64 字节，采用截断模式，并明确在索引 63 写入 NUL。
- `0x1405C71B3`–`0x1405C7215`：对格式化结果计算 hash，传入人物 GUID 和实际技能档数，查询购买等级。
- 公会查询 `0x1406742C9`–`0x1406742DE` 使用相同的有界目标；`0x140674330`–`0x14067433F` 按 hash 继续保留最后匹配树。
- 升级树注册 `0x14046FEE6`–`0x14046FF21` 虽然拷贝一个有界名称用于保存文本，但 hash 循环仍读取原始 JSON 字符串。不能把“构造查询目标要截断”扩大成“所有升级树 ID 注册时都截断”。

新提取片段保存在 [本轮原生证据目录](../../workspaces/historical-rule-review15-20260911/)。独立校验脚本还直接调用本机 UCRT 的 `__stdio_common_vsnprintf_s`，验证全部 102 组目标；没有在游戏进程里调用函数。

### 历史来源与建议边界

`git blame -C -C -C` 将完整目标拼接追溯到仓库最早可见提交 `7b9a67f`。之后隐式技能兼容、文件拆分和逐树最后匹配解析保留了该假设。`c44aea4` 的授权范围仅修复露营购买目标，没有修改战斗目标。

建议同时修正战斗技能的目录绑定、显式／隐式购买目标和相应可用性校验。保留原技能 ID、原始树定义 ID 和通用保存 hash；不能只在写入时截断，也不能全局修改所有资源的 hash 算法。隐式技能帮助函数当前通过 `treeId[(heroClass.Id.Length + 1)..]` 反推技能 ID，后续实现有界目标时还需保留独立的原始技能身份，避免查错其实际档数。

## 2. P2：已有战斗技能树的校验把“存在可买条目”当成“技能已能解锁”

### 触发与影响

[当前预检](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs#L39)仅在该等级没有任何可购买 requirement 时拒绝。随后[购买计划](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs#L59)照抄所有满足等级门槛的原始 code。

这可以正确保存 code 本身，却没有验证普通战斗技能是否能消费它们：

| 短名称树的已购 code | 编辑器当前结果 | 原生技能等级查询 |
| --- | --- | --- |
| `0, 1` | 允许生成 | 第 1 档，正常 |
| 只有 `A` | 允许生成 | 缺少 `0`，返回未解锁 |
| `a, A` | 允许生成 | 缺少 `0`，返回未解锁 |
| `0, 2`，技能定义共三档 | 允许生成且没有升级空洞提示 | 缺少 `1`，停在第 0 档 |
| `1` 已符合门槛、`0` 要到人物 3 级才能购买 | 人物 1 级也允许生成 | 仍缺少 `0`，返回未解锁 |

对照还包含正常延后购买的数字树、连续三档数字树、所有需求均未达门槛和空树：正常树得到对应档数；后两类既有保护仍正确拒绝生成。

这些反例均使用短技能 ID，排除了第一项名称截断的影响。编辑器的技能选择列表已包含该技能，写入记录也有正确 GUID／正确短目标 hash，问题仅在购买码序列不满足实际查询。

### 原生证据及历史测试缺口

`0x14058EA10` 的非“全部已购”分支从字符 `0` 开始查询，逐个递增，并在第一条未购买记录或实际技能档数边界停止。它不按升级树 requirement 数量或数组顺序重编号：

```text
last = 未解锁
依次查询 code '0', '1', ...，最多检查实际技能档数：
    若该 code 未购买：停止
    last = 当前档数
```

`0x1405C721A`–`0x1405C7230` 将返回字符转换成从 0 开始的技能档数；没有基础码时写入 `-1`。

这是 [隐式技能研究](../implicit-skill-progression.md) 已有的原生消费规则。当前隐式分支已据此检查连续数字，但已有树分支仍保留仓库最早可见版本的“任意 requirement 可买即可”判断。因此不是需要撤销多数规则，而是需要补齐已有树的消费校验。

后来的 [升级树合同测试](../../tests/DarkestDungeonSaveEditor.ContractTests/HeroUpgradeTreeContractTests.cs#L87) 使用 `a/A` 验证原始大小写和最后匹配，并在 [保存断言](../../tests/DarkestDungeonSaveEditor.ContractTests/HeroUpgradeTreeContractTests.cs#L130)确认这两个 code 被原样写入。那些断言能证明读取身份和 DSON 保存，却不能证明战斗技能解锁；目前还把这种计划“可生成”当成通过条件。

建议保留通用树解析和 code 的原样保存，在战斗技能生成环节验证基础解锁及可到达档数。无基础码时不能继续声称全技能解锁；有空洞时需要明确说明实际只能到达较低档，或按产品既有严格生成约束拒绝。不应把 `A/a` 自动改成数字、擅自补写不存在的已购等级，也不能对装备或所有升级树全局禁止字母 code。正式测试应分别覆盖“定义原样读取”和“生成计划确实能被消费”。
