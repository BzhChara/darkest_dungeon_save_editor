用户要求在当前 `profile_1` 中置顶一个古董商特殊升级 Mod，实际启动游戏验证。游戏从 Steam 启动；本轮只验证技能树规则，不将新的升级树解析逻辑接入编辑器。

## 已观察结果

两组中，公会里的七项战斗技能都显示 `10,985` 金币，邦瓦莱可购买下一档升级。公会训练技法已有两档，显示价格与 `13731 × 0.8` 取整一致。未购买技能、升级建筑或推进周数；两组画面金币均为 `357,860`。

这证明不同路径的置顶技能树也能被游戏采用。同路径对照同样生效，不能把第一组误认为只有原版文件覆盖才有效。

移除测试 Mod 后再次从 Steam 进入同一档案，七项下一档技能重新显示锁定；第一项的提示明确显示“英雄决心等级：1”，验证等级要求已恢复。锁定状态没有显示购买价格，因此不将推算的原价写作实测结果。金币仍为 `357,860`。

## 原生代码核对

本轮使用已有 MSVC `dumpbin` 读取该版本游戏程序，未注入或修改游戏内存：

1. `0x1403E8883` 附近使用 `.*upgrades/.*\.upgrades\.json$` 枚举升级文件，随后逐文件调用 `0x14046FA80`。
2. `0x14046FA80` 读取 `trees`，每棵树追加到全局数组。数组首尾地址为 `0x142C25AE0` / `0x142C25AE8`，单项大小 `0x70`。加载处没有按“最适合人物”选择一整个文件。
3. 公会函数 `0x1406741C0` 将 `<class>.<skill>` 算成游戏 ID 哈希；`0x140674330` 比较树的哈希，`cmove` 更新匹配指针，循环继续到数组末尾。因此最后一条匹配树被采用。
4. 升级条件查询 `0x1404703D0` 同样遍历全部树、保留最后匹配项，再从该树查询购买代码。

树查找的确定结论是“按有效加载顺序，逐个树 ID 取最后匹配”。Mod 列表顺序先参与文件路径覆盖及枚举；不能简单替换为“每个英雄只挑优先级最高的一整份升级文件”。不同文件可以分别提供同一英雄的不同树。

## 对编辑器现有兼容的影响

`HeroClassCatalog.Progression.cs` 中的 `SelectCompatibleHeroUpgrade` 按装备要求、技能树匹配数量挑选整份模板，是编辑器的推断，不能作为游戏规则。本次置顶完整模板的成功并不单独覆盖“同一 Mod 多份树”“部分覆盖”“任意升级文件名”等全部情形；原生查找代码为按树解析提供了直接依据。

后续接入应按有效文件顺序解析所有树，保留树 ID 和具体来源，再为人物的每个技能/装备寻找对应树。修改时需增加部分树覆盖、同一 Mod 多文件、重复树 ID 和购买代码的回归。现有树缺失时的隐式技能购买兼容属于另一条存档写入路径，本次没有验证它应当删除。
