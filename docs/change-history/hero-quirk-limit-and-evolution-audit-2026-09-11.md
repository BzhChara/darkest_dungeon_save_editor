# 历史修改第十七轮审核：人物怪癖数量与进化判定

审核基线：`85db21d`（`fix: align native equipment purchase progression and save guards`）。本轮先提交上一轮装备修复，再只读审查人物生成中的旧规则。确认两项需要修改的问题；本轮未修改产品源码。

## 结论

| 优先级 | 已确认问题 | 影响 |
| --- | --- | --- |
| P2 | 初始怪癖数量上限固定为 5 / 5 / 3，没有读取活动 shared 规则 | Mod 提高上限时误拦；降低上限时仍允许按旧上限生成；修改上限后，人物保存校验不能识别语义变化 |
| P2 | 进化检查把字段前缀、显式默认值和空目标过度解释为不完整配置 | 普通怪癖与有效的到期死亡怪癖可能被标为不可显式写入 |

另外核对了 `slot_size`：游戏内新增怪癖的槽位消耗与读档时的条数检查不是同一个消费者。**本轮不把按条数计数列为独立错误，也不建议直接改成 `slot_size` 求和。**

## 1. 初始怪癖上限未使用活动规则

### 当前代码和历史来源

- `src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.cs:9–11` 固定正面 5、负面 5、疾病 3。
- `StagecoachHeroCandidateFactory.Quirks.cs:54–63` 使用这三个常量拒绝选择。
- `src/DarkestDungeonSaveEditor.App/InitialQuirkSelectionDialog.xaml.cs:298–300` 显示相同常量。
- `HeroClassCatalog.SourceDiscovery.cs` 的来源集合没有 shared 全局规则；`HeroClassCatalogResult` 也不携带有效数量上限。
- `SaveEditService.StagecoachHeroes.cs:325` 计算人物目录指纹时没有这些上限。

常量在 `7b9a67f` 初始基线中已经存在，`827ca42` 拆分文件后继续保留。不是本轮提交的装备修复引入的回归。

### 游戏证据

本地 x64 build 27890：

- `0x1404E81F0` 加载 shared 规则；离线查询目录为 `shared/`，文件表达式为 `.*rules.json`。不能把后续实现简单限定为唯一的根目录 `shared/rules.json`。
- `0x1404E9BB6–0x1404E9CA1` 读取 `quirks_max_positive`、`quirks_max_negative`、`quirks_max_diseases`，分别写入 `0x142AC7778`、`0x142AC777C`、`0x142AC7780`。
- `0x1405C1D40` 的新增怪癖流程使用这些上限。
- 人物读档 `0x1405C5200` 调用 `0x1405C9830`，后者也使用这些配置值进行条数检查。不能把“游戏读档会在任何情况下统一裁剪三类怪癖”当成已证明的结论：该函数还有前置分支，本轮没有把它简化为统一裁剪模型。

原版 `shared/rules.json` 恰好填 5 / 5 / 3，所以原版常规值会掩盖这个问题。

### 隔离复现

全部怪癖定义均存在、无互斥、无未知 Buff。Mod 来源的定义和规则文件均明确列在 `modfiles.txt` 中。

| 配置与选择 | 当前编辑器 |
| --- | --- |
| 正面上限 6，选择 6 个普通正面怪癖 | 拒绝，提示最多 5 个 |
| 负面上限 6，选择 6 个普通负面怪癖 | 拒绝，提示最多 5 个 |
| 疾病上限 4，选择 4 个普通疾病 | 拒绝，提示最多 3 个 |
| 任一类别上限改为 1，选择该类 2 个普通条目 | 仍允许生成，配置没有影响验证 |

在已有目录与预览之后，只把同一规则文件的正面上限从 5 改成 2，不改清单：

- `ProfileCatalogContentFingerprint.Capture` 的刷新信号改变。
- 重新加载人物目录后，`ComputeHeroCatalogSha256` 不变。
- `ValidateStagecoachContentGuard` 不拒绝旧预览。

所以这不是自动同步监控不到文件；根因是目录没有读取有效上限，重新解析仍丢失相同语义。

### 建议修改范围

按有效 shared 规则的原生查询、清单资格、同路径覆盖和装载顺序读取上限，让目录、选择窗口、生成检查和保存前校验使用同一份结果。保留按当前产品策略检查数量的能力，不宜只删除三条上限检查，也不能把它改为职业 `generation` 中的随机初始怪癖数量。

## 2. 进化兼容检查误拦默认配置

### 当前代码和历史来源

`HeroClassCatalog.QuirkDefinitions.cs:392–447`：

1. 任意 `evolution_` 前缀字段都会使 `ReadEvolutionSignature` 返回非空。
2. 随即强制要求持续时间上下限和一个进化结果。
3. 只要出现 `evolution_class_id`，它就必须是非空字符串，即使结果已经明确为死亡。

这套检查由 `a07b5c0` 的人物怪癖生成功能引入，后经 `1a03bb4` 拆分。`c14247a` 修正了字段大小写及同名 JSON 属性取值，但没有修正上述启用判定。该次大小写/首属性修复仍应保留。

### 游戏证据和复现

原生构造器 `0x1404E02E0` 把持续时间、目标哈希、死亡标志初始化为零。`0x1404DDBF0` 按具体字段名查找，不把任意前缀字段当成进化声明。

- `0x1404DEE30` 起读取具体的持续时间字段。
- `0x1404DF0A3–0x1404DF0C1` 把空 `evolution_class_id` 解析为目标哈希 0，与省略字段的默认值相同。
- `0x1404DF0C7–0x1404DF149` 独立读取死亡布尔值。

隔离目录中的普通怪癖 `q0`，增加以下内容后都会被编辑器拒绝：

| 增加内容 | 原生解析后的进化状态 | 当前拒绝原因 |
| --- | --- | --- |
| `"evolution_note":"author note only"` | 已知进化字段保持普通默认值 | 缺少持续时间与进化结果 |
| `"evolution_causes_death":false` | 与省略该字段一致 | 缺少持续时间与进化结果 |
| 持续时间 0 / 0、空目标、死亡 false | 与普通默认状态一致 | 空目标、缺少结果 |

另一个不依赖“是否启用进化”推断的对照：

```json
{
  "evolution_duration_min": 12,
  "evolution_duration_max": 12,
  "evolution_causes_death": true
}
```

上述到期死亡定义能生成，并把剩余持续时间 12 写入临时存档。只增加 `"evolution_class_id":""` 后，游戏仍解析出相同的六个进化字段值，编辑器却报“必须是非空字符串”。

这里比较的是固定版本的原生解析状态与已运行的编辑器结果；本轮没有启动游戏等待死亡进化发生。

### 建议修改范围

按游戏实际读取的已知字段及默认值判断进化状态，忽略不参与机制的前缀备注；空目标应与默认无目标区分于真实的缺失目标引用。保留对有效进化链中真实目标缺失、无效 ID 和无法安全初始化状态的检查。不能通过简单删除全部进化校验来修复。

## 3. 核对后不应直接修改的规则：slot_size

庭院原始定义 `disease_vampire_passive`、`disease_vampire_crave`、`disease_vampire_wasting`、`disease_vampire_blood_lust` 都有 `slot_size: 3`。这确实会影响疾病槽消耗：

- 原生定义读取 `0x1404DFADA–0x1404DFB54` 把 `slot_size` 写入 Quirk class 的 `+0x1B4`；默认值为 1。
- 新增疾病的计数函数 `0x1405C1C90` 累加该字段；正负怪癖新增流程也使用槽位总和。
- 读档检查使用 `0x1405C4860` 收集每条匹配怪癖的索引；每条只加入一次，并不展开 `slot_size`。
- 三个分类谓词 `0x1404E0D50`、`0x1404E0D10`、`0x1404E0BF0` 分别读取正面、负面且非疾病、疾病标志，没有槽位求和。

因此，“猩红诅咒加一个普通疾病占 4 槽”不能单独证明编辑器把两个条目写进存档就是错误，也不能据此声称游戏必然在读档时删除某条。零槽位怪癖同样不能据此绕过独立的条数检查。隔离探针中的这四类槽位样例已作为对照，不计入确认缺陷。

仅修改 `slot_size` 时，刷新信号改变而人物保存指纹不变，也不能独立作为当前生成规则的错误证据。本轮对此不提出产品修改。
