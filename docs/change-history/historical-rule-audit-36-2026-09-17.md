## 1. P2：人物 Buff 读取失败会回退旧定义，过期 HP 仍能保存

位置：`HeroClassCatalog.cs:147–159,248–253`、`SaveEditService.StagecoachHeroes.cs:249–287,341–356`。

人物目录捕获 Buff 文件的读取异常后，只向 `Issues` 添加文字，没有保留该加载位置的不确定状态。随后 `ResolveOrderedDefinitions` 在成功读到的候选中选最后一条。若失败的文件原本应提供最后一条同 ID Buff，较早定义就被重新当作完整、可写入的有效定义。保存校验重新加载相同的不完整目录，而目录哈希不包含读取完整性，因此也可能通过。

已经复现两种情形，Base、本地 Mod、工坊 Mod 均一致：

- `a.buffs.json` 定义 `hp_buff`，生命 +50%；`z.buffs.json` 再定义同 ID，生命 +100%。基础 HP 20，全部可读时应为 40。独占打开后一文件使编辑器无法读取，目录仍允许该怪癖，新人物实际写入 `current_hp=30`；释放锁、不改变任何定义字节，再读恢复为 40。
- 更贴近日常操作的保存边界：最初后一文件是空 Buff 列表，正常捕获资源指纹、加载目录并生成 HP 30 的预览。随后把后一文件更新为 +100% 并暂时占用。再次预览与提交原先的健康预览都获准，DSON 回读仍是 30；释放后目录为 40，资源指纹也确实变化。说明问题不能靠定时刷新兜底，它发生在写入前的重新解析中。

相反，原预览已经采用 HP 40，再占用后一文件使解析变成 30 时，已有哈希比较会拒绝预览和提交，三个存档文件保持逐字节不变。只有较早文件读取失败、后面存在明确同 ID 完整定义的对照仍正确得到 40。修复不能简单禁止所有出现任何诊断的目录，也不能恢复被覆盖的下层文件。

建议：把有效文件读取失败及其加载位置传递到 Buff 定义解析和所选怪癖的写入状态；不能确认最终定义时拒绝相关候选及保存。保留后续明确完整定义能够重新确定该 ID 的情况，不把日志文本是否存在当作统一开关。

历史定位：捕获后仅记录日志的代码可追溯至仓库初始提交 `7b9a67f`。后续“Buff 最后完整定义优先”及保存目录重读没有补齐失败位置语义。刚提交的 `3f3db14` 修复了饰品依赖存在性及 HP 枚举解析，并未引入这段人物目录回退。

## 2. P2：怪癖引用仍混用字符串与原生哈希，既会误拦也会漏掉互斥

位置：`HeroClassCatalog.QuirkDefinitions.cs:43–47,75–90`、`StagecoachHeroCandidateFactory.Quirks.cs:76–82`。

当前游戏对 `buffs`、`incompatible_quirks`、`evolution_class_id` 都计算到 NUL 为止的原生字节哈希。编辑器的 Buff 查找、进化链目标查找和怪癖互斥比较仍使用完整字符串；进化目标已截断 NUL，但仍未处理同哈希的引用别名。

实验只声明一个实际 ID `Az`，引用分别使用 `Az`、`BE`、`Az\u0000tail`、`BE\u0000tail`，另加真正不同的大小写、空白及不存在 ID 对照。`Az` 与 `BE` 的原生哈希同为 3567；这不是两份定义发生冲突。

- **Buff 引用**：游戏能找到提供 +50% HP 的 Buff，编辑器却报缺失并禁止选择，预期 HP 30 的正常候选被拦截。
- **进化目标**：同哈希目标已存在，编辑器仍报进化链缺失；单纯 NUL 尾缀已截断的对照正常。
- **互斥引用**：怪癖 `other` 的互斥列表指向 `BE`，实际怪癖是 `Az`，编辑器仍允许二者同时选择。已通过 `Generate → PrepareStagecoachHeroEditAsync → CommitAsync → DSON decode`，确认两个互斥记录一起进入合成 town 存档。这里没有推断游戏载入后会崩溃或自动删除哪一个。

三种来源共 63 个样本，24 处不符：Buff 引用 9、进化目标 6、互斥引用 9。正常拼写和真正不同身份的对照符合预期。

建议：按每个消费入口已证明的 C-string 哈希解析引用，映射回实际定义用于显示与保存；不要全局转小写、修改保存 ID 或取消真实定义冲突保护。互斥判断、进化链追踪和 HP 依赖应同时接入，避免只修正目录显示。

历史定位：Buff 字符串查找来自 `1a03bb42`，进化链查找来自 `730c01eb`；`78fd748a` 修正了大小写敏感性，但互斥分支仍是原始字符串比较。此前修正“大小写不同就是不同输入”没有覆盖“不同字符串可能表示同一个原生哈希引用”，无需回滚正确的大小写修复。

## 3. P2：职业来源不完整时，饰品仍将“不知道”当成“职业不存在”

位置：`TrinketCatalog.cs:26–28,124–130`、`ActiveContentResolver.cs:114–144`。

上一轮已为普通 Buff 依赖接入 `HasUnresolvedModSources`，但职业依赖仍只检查 `heroIds` 集合。已启用 Mod 因标题歧义、无法映射或工坊目录不可用而未进入 `Sources` 时，发现的职业集合不完整；缺少某个 ID 并不能证明该职业确实不存在。

隔离档案中，第一条 `audit_trinket` 需要 `mod_hero`、使用次数 2；后面同 ID 条目无职业要求、次数 7，两条普通 `buffs` 都为空。通过实际 `ActiveContentResolver.ResolveAsync` 入口验证：

| 来源情形 | 编辑器结果 | 保存验证 |
| --- | --- | --- |
| 唯一、正常映射的本地 Mod 提供职业 | 第一条，次数 2 | 正常保存 2 |
| 两个本地目录同标题，均提供该职业，映射被判歧义 | 跳过第一条，选择 7，未标只读 | 仍保存 7 |
| 已启用本地标题无法映射 | 同上 | 仍保存 7 |
| 已启用工坊来源目录不可用 | 同上 | 仍保存 7 |

后三种应保留依赖不确定性，而非证明后面的条目获胜。这里不宣称所有缺失来源在游戏里都必定采用次数 2；错误是来源尚未确定，编辑器已把 7 当成经过验证的最终定义。已有 `ValidateSourceBindings` 只会发现映射发生变化，持续相同的缺失或歧义不会触发它。

建议：职业依赖也区分存在、确认不存在、来源未完整解析，只有确认缺失才跳过条目。相关未知依赖应使原候选只读，而不能改变同 ID 首条选择。预览、提交都保留真实 `Resolution` 上下文；无需增加旧存档兼容。

历史定位：存在性失败直接 `continue` 来自 `4e1db6b`。`3f3db14` 正确修正了职业引用的哈希身份，但完整性只应用到了 Buff 依赖，因此这条相邻路径仍有遗漏。
