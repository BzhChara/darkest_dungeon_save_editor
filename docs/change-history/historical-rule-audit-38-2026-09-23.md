## 1. P2：露营定义读取失败仍可改变技能池并通过人物保存

位置：[露营定义读取](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.cs)，183–201 行；[分类与适用职业](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.InternalModels.cs)，350–364 行；[选择与购买计划](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs)；[预览与提交重读](../../src/DarkestDungeonSaveEditor.Core/SaveEditService.StagecoachHeroes.cs)，30–44、280–288、341–356 行。

读取异常只进入 Issues，剩余技能继续参与分类和生成。这里有两种已经实际保存的错误：

1. `a.camping_skills.json` 首次声明 `rest` 为职业技能；`z.camping_skills.json` 再声明相同 ID 为共享技能。完整读取时按首条分类，人物要求“职业 0、共享 1”，不应选中 `rest`。首文件被独占打开后，编辑器把后条当成首条，共享池出现 `rest`，并写进 `selected_camping_skills`。
2. 首文件原为空，后文件有 `rest`，健康预览已生成。首文件随后新增适用当前职业的 `extra`，但暂时无法读取；目录继续只报告 `rest`。旧预览和重新预检均通过，保存的购买记录缺少 `review_hero.extra`。释放锁后完整目录的生成计划包含这条解锁记录。这里核对的是编辑器既定“解锁全部有效露营技能”策略，不依赖随机种子是否应抽到某个技能。

Base、本地、工坊均完成以上两类 DSON 提交，共 6 次。另以 `ResolveAsync` 从编码后的 `persist.game.json` 启用列表解析真实的合成本地标题和工坊 ID，保留 `Resolution`、清单和源绑定校验，再各复现一次错误提交；不是只有手工指定来源列表才发生。

所有问题预览均先在完整可读配置中建立，再更新资源并制造读取故障；清单、来源路径及顺序未改变。读取故障使重读结果恰好退回原预览，目录哈希未包含相应不确定性，故预检/提交没有拒绝。8 组已经采用更新定义的负对照全部拒绝，存档字节不变。

历史定位：仅日志捕获来自初始提交 `7b9a67f`。`27a6c17` 修正为首条分类并累计适用职业，但未补文件完整性。`6cf2425` 将真实技能池不足改为有界少取，规则符合已研究的游戏行为；问题是读失败也被误当成真实不足，**不应通过恢复“数量不足就禁用人物”的旧补丁修复**。

建议：同时表达首条分类、累计职业适用范围和技能池完整性；不完整集合不能据此确认抽取/全部解锁计划。让生成、预检和提交观察同一状态，同时保留完整资源下正常少取与各池独立抽取。

## 2. P2：Effect 文件读不到会重新显示已被清空的运行时怪癖线索

位置：[Effect 读取](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.cs)，111–123 行；[疾病字段与线索绑定](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.QuirkDefinitions.cs)，198–241 行；界面使用 `MainWindow.RowModels.cs:122–127` 和 `MainWindow.CatalogInteraction.cs:70`。

复现：前文件 `probe_effect` 的 `.disease` 为 `runtime_q`，后文件同名 Effect 明确设置 `.disease ""`。正常目录没有这条线索；只占用后文件，日志虽报告失败，人物的 `RuntimeQuirkSignals` 却重新出现 `runtime_q`，继而影响显示、搜索与统计。释放锁后再次消失。

六种来源的后文件占用均复现，三个 Mod 来源的有效清单项缺失也复现。只占用前文件而后文件明确清空的对照没有误报。该问题影响人物技能相关线索，**不等于上次怪癖定义/HP/排斥/进化的修复失效**，本轮未据此声称初始 HP 被错误写入。

历史定位：仅日志异常处理同样来自 `7b9a67f`；后来接入逐字段覆盖及显式清空规则时，没有让失败文件保留不确定性。建议按疾病字段的赋值顺序处理未知位置：后续明确赋值可重新确认，省略字段不能当成明确清空；无法确认的旧线索不应作为已确认结果展示。不要改回“整条 Effect 最后覆盖”的旧理解。

## 3. P2：招募事件读取失败会采用后面同 ID 的招募结果

位置：[事件读取与首条选择](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.cs)，227–239、285–300 行；[事件结果解析](../../src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.SupportingDefinitions.cs)，51–108 行；界面使用 `MainWindow.RowModels.cs:121` 和 `MainWindow.CatalogInteraction.cs:69`。

复现：前文件的 `audit_recruit` 没有 `bonus_recruit` 数据，后文件同 ID 事件包含“招募当前职业 2 人”。完整读取时首条占位，目录不应将后条结果列为人物招募线索。前文件锁定、损坏或清单项缺失后，编辑器略过它，将后条的数量 2 和事件关联标为有效；恢复读取后关联消失。

六种来源的占用/JSON 损坏及三个 Mod 来源的清单项缺失均复现；首条完整可读、只占用后文件时正确保留无招募结果。此处影响目录、搜索和招募来源说明，不声称编辑器已经实际触发游戏事件或改变游戏的随机事件池。

历史定位：捕获并继续处理的逻辑源于 `7b9a67f`；`c14247a` 扩展异常类型，后续 first-result 修复也没有处理未知首条位置。建议保留失败的事件文件槽位，防止不确定的后条冒充首条结果；已在故障前完整确认的首条仍可使用。游戏随机事件池与按 ID 执行结果仍是两个问题。

## 已检查但不建议删除的保护

- 人物规范 `.art` 的读取故障会向外报告失败，未恢复成 info 中的旧 HP。Base、本地、工坊均做了正常 HP 40 与占用拒绝对照。
- 容量文件读取故障返回未知容量；三类来源均验证，未采用旧容量继续写入。没有为减少拦截而建议删除这项保护。
- 共享同步的资源指纹会观察这些文件变化；问题不在轮询周期。保存入口仍必须独立识别不完整目录，不能依赖下一次自动同步先发生。
- 上轮首条物品/饰品、末条怪癖/升级树的读取状态仅覆盖对应四类定义。本轮没有重新把相同代码报告为未修复，也没有把露营的“首条分类 + 累计适用职业”、Effect 的逐字段保留、事件的首条执行结果强行统一。
