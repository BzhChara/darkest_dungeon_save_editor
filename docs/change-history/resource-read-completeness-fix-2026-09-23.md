# 资源定义读取失败与保存完整性修复（2026-09-23）

基线：`619c5357f5f84f28801d669f62701688eff78497`。用户确认修复[第三十七轮审核](historical-rule-audit-37-2026-09-17.md)的四项问题。本次处理有效资源定义文件自身无法读取时的错误回退；此前 Buff 属性读取、饰品依赖与同路径文件覆盖的保护继续保留。

## 行为与代码

- `OrderedDefinitionReadState.cs`：共用有序读取状态。first-match 在故障前已确认的首条仍可信，故障后新遇到的 ID 不可证明；last-match 遇到故障后清除此前的确认状态，后续完整定义可重新确认自身 ID。无法确定文件顺序时不作位置推断。
- `HeroClassCatalog.cs`：怪癖文件完整解析后才发布候选；不完整的最后匹配结果不再用于初始 HP、排斥和进化链，也不再确认为运行时怪癖线索。
- `HeroClassCatalog.Progression.cs`、`.InternalModels.cs`、`.HeroDefinitions.cs`：升级树携带读取状态；武器、护甲、技能目标在读取不完整时显式不可用，不能用较早条件，也不能把未读到当成确认没有树。
- `TrinketCatalog.cs`：整文件读取失败时，后续同 ID 的次数不再被误认成首定义；已经在失败前确认的首定义仍可使用。原依赖淘汰、次数默认值和不合并后续字段的规则保持不变。
- `QuantityItemCatalog.Definitions.cs`：同样保护普通有定义物品的首匹配堆叠上限，将解析顺序问题传入仅存档条目的完整性状态；整文件读取成功后才加入候选。小镇钱包聚合和副本分格使用现有逻辑。
- `DefinitionReadCompletenessContractTests.cs` 及两处套件接线：增加三类来源、四类定义的目录、预览、保存、回滚与恢复验证。规则更新于 `docs/content-save-rules.md`、`docs/resource-duplicate-semantics.md`，测试说明更新于测试目录 README。

保存服务原有的生成结果校验、提交前重读和替换后检查现在能够观察这些不可用状态，无需另加一套提交逻辑。物品保存数量的增量刷新保留相应标记。

影响流程是目录可写状态、人物生成、预览和实际保存。清单准入、原生文件顺序、同路径覆盖、重复 ID 的 first/last 规则、战斗编号、Bridge 与自动同步调度没有改变。没有旧存档迁移，没有修改用户真实存档、安装的 Mod 或游戏文件。并非所有异常都禁用所有资源：仍能确定赢家的条目保留使用，重新完整读取后恢复正常。
