# 历史修改第十八轮审核：怪癖计数、概率分类与候选保存边界

审核基线：`11ab3eb`（`fix: honor active quirk limits and native evolution defaults`）。已先提交上一轮活动怪癖上限、进化默认值及保存校验修复，再审查遗留实现。本轮没有修改产品源码或正式测试。

本轮确认两项解析／消费差异，另记录一项只在特定 Core 接口组合下复现的 HP 校验缺口。范围是人物目录、初始怪癖选择、候选生成及马车保存；不是整个项目所有路径都已验证正确的结论。

| 优先级 | 已确认问题 | 触发条件与影响 |
| --- | --- | --- |
| P2 | 正面怪癖计数错误地排除了疾病 | 同一怪癖同时声明 `is_positive:true` 和 `is_disease:true` 时，编辑器少算正面数量，允许超出正面上限并保存；选择摘要也少算 |

## 1. 正面疾病没有参与正面上限

### 当前实现与历史来源

`src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Quirks.cs:54` 使用：

```csharp
selected.Count(quirk => !quirk.IsDisease && quirk.IsPositive == true)
```

相同的互斥分类还用于：

- `StagecoachHeroCandidateFactory.cs:154` 起的候选正面怪癖列表；
- `src/DarkestDungeonSaveEditor.App/InitialQuirkSelectionDialog.xaml.cs:292` 起的选择数量摘要；
- 保存预检调用相同的 `ValidateInitialQuirkSelection`，因此不会拦下这一差异。

该表达式在初始基线 `7b9a67f` 中已存在，`827ca42` 拆分文件后沿用。刚提交的 `11ab3eb` 改成读取活动上限，但保留了原有分类表达式。**这是旧计数规则的遗漏，不应回滚活动上限修复。**

### 游戏证据

固定 x64 build 27890 的三类计数谓词：

| 类别 | 函数 | 条件 |
| --- | --- | --- |
| 正面 | `0x1404E0D50` | 仅读取定义 `+0x50` 的正面标志 |
| 负面 | `0x1404E0D10` | 正面标志 false 且疾病标志 false |
| 疾病 | `0x1404E0BF0` | 仅读取定义 `+0x51` 的疾病标志 |

本轮重新读取 PE 虚表，确认三个 wrapper 的调用槽确实指向上述函数；`0x1405C4860` 按谓词收集每条怪癖的索引。`0x1405C9830` 将正面结果的条数与活动 `quirks_max_positive` 比较。不是仅凭相邻函数地址猜测用途。

怪癖加载器 `0x1404DDBF0` 在 `0x1404DE632` 与 `0x1404DE678` 分别写入两个布尔值，没有在这里把正面疾病强制改为负面。因此正面疾病参与正面和疾病两项计数；负面疾病仅参与疾病计数。

该计数不等于按 `slot_size` 求和，上一轮对此的区分仍应保留。这里也没有把原生读档清理过程泛化为“任何条件下必定裁剪全部三类”：`0x1405C9830` 自身还有分支。

### 已执行的复现

所有怪癖均存在、无互斥和未知 Buff；使用完整原版怪癖模板替换 ID、两个标志、概率和引用，避免靠省略必需字段制造差异。Mod 测例的资源均写入 `modfiles.txt`。

| 上限与选择 | 原生谓词计数 | 当前编辑器结果 |
| --- | --- | --- |
| 正面上限 0、疾病上限 1，选一个正面疾病 | 正面 1，疾病 1，正面超限 | 允许，摘要正面 0、疾病 1 |
| 正面上限 1、疾病上限 1，选普通正面 q0 和正面疾病 q1 | 正面 2，疾病 1，正面超限 | 允许，摘要正面 1、疾病 1 |

在本体、mode、dlc-feature、local、workshop、启用 DLC 子路径的 Mod 六类来源中，两个错误样例均复现，共 12 例。其余 36 个计数对照符合预期。

建议统一核心验证与界面计数为原生谓词。疾病仍可以在界面单独展示，但用于上限的正面计数不能把它排除。尚未修复；未验证当前真实 profile_1 是否包含此类 Mod 怪癖。

## 2. 极小概率误分类并遗漏运行时线索

`HeroClassCatalog.QuirkDefinitions.cs:260–265` 使用 `TryGetDouble` 后直接保存 `randomChance`。`BuildInitialQuirk` 以大于零判断 Natural；`ResolveRuntimeQuirk` 以大于零排除运行时特殊怪癖线索。

原生 `0x1404DE5DF` 读取 JSON 数字，`0x1404DE5E7` 使用 `cvtsd2ss` 转换为单精度，再写入怪癖定义。现有 Buff 数值读取已经通过 `ReadJsonFloat` 做同类转换；怪癖概率仍遗漏这一处理。

历史上直接存 double 的代码在 `1a03bb4` 拆分时已经存在。`c14247a` 改进同名 JSON 属性查找时没有改数值精度。不能因此撤销首个精确属性匹配规则。

隔离人物技能 c 引用 Effect `AuditGrant`，后者 `.disease "q0"`；只改变 q0 的概率：

| 概率文本 | 原生 float32 | 编辑器分类 | 编辑器运行时线索 |
| --- | --- | --- | --- |
| `0` | 0 | 固定／特殊 | 正确保留 q0 / AuditGrant / c |
| `1e-50` | 0 | 错误标记自然随机 | 错误遗漏上述线索 |
| `1e-30` | 正数 | 自然随机 | 按既有策略不收集特殊怪癖线索 |
| `1` | 1 | 自然随机 | 按既有策略不收集特殊怪癖线索 |

六类来源下各复现一次，共 6 例差异，18 个普通概率对照一致。问题只需要正常的数字 JSON，不依赖非法字符或缺失文件。

影响限于概率解析、自然／特殊分类及以此为前提的运行时线索搜索／显示。编辑器显式选择初始怪癖不会因此随机多生成一个，也没有证据说明当前真实 Mod 使用了这一数值。建议复用已有单精度读取规则，不改变重复 ID、同路径覆盖、清单资格或 Effect 合并行为。

## 3. 额外接口边界：旧候选配上新目录仍可保存旧 HP

**这是 Core API 组合下复现的校验缺口，本轮不计为当前正常界面流程中的故障。**

`SaveEditService.StagecoachHeroes.cs:292` 起的预检核对职业、等级、装备购买计划与怪癖可写性，但不会将候选 JSON 中已经生成的 `actor.current_hp` 与当前定义重新计算的初始 HP 比较。现有装备一致性校验检查的是当前目录内部的一致性，不能替代候选 HP 核对；怪癖检查也只验证计算能否通过，没有比较保存值。

两组隔离测试均执行了完整保存：

| 内容变化 | 旧候选 HP | 按新目录重新生成的 HP | 把旧候选传给新目录后实际保存 |
| --- | --- | --- | --- |
| 基础 HP 20，怪癖 Buff 从 +25% 改为 +50% | 25 | 30 | 25 |
| 相同护甲档位的 HP 从 20 改为 40 | 20 | 40 | 20 |

两组都同时验证了保护对照：

1. 内容变化后提交旧 prepared edit：正确拒绝，三个源存档哈希不变。
2. 用旧目录和旧候选重新准备：正确拒绝，提示模板变化。
3. 显式调用 Core 接口，把旧候选与重新加载的新目录组合：允许准备和保存，HP 仍是旧值。

当前 `src/DarkestDungeonSaveEditor.App/MainWindow.EditWorkflow.cs:168–180` 从同一份 `_heroCatalog` 先 Generate 再 Prepare，并有界面版本检查；没有上述第 3 步复用旧生成对象的路径。因此不能把这项结果解释为“普通用户更新 Mod 后，新人物一定会用旧 HP”。

后续若开放候选缓存、重试或外部调用，可考虑绑定候选的目录指纹，或在保存入口核对实际候选 HP；不应删除现有目录指纹保护。本轮只记录边界，不把它扩展为其他人物字段也已验证。

## 4. 核对后保留的限制

- 缺失 `is_positive` 仍不应直接按原生构造器默认 false 放行。原生加载器还会走缺失／类型错误的诊断路径；尚未完整确认该诊断后的行为，不能把“内存初值 false”扩大成“此字段可合法省略”。
- 活动怪癖上限、已修复的进化默认值、缺失进化目标校验和预览指纹保护均有独立目的，不应整体删除。
- `slot_size` 的新增怪癖槽位成本与按条数计数仍需区分，不能通过更换成槽位求和修复正面疾病计数。
