## 1. P2：饰品遗漏缺失 Buff 的原生淘汰规则

位置：`TrinketCatalog.cs:119–163`、`SaveEditService.Trinkets.cs:44–63`、`SaveEditService.Trinkets.cs:325–355`。

饰品扫描检查职业要求后直接建立候选，不检查普通 `buffs` 列表指向的 Buff 是否存在。新版游戏的饰品加载器会逐个查找这些 Buff；任一引用缺失就将整条饰品标为无效，最终不加入可供查找的饰品列表。

具体反例（ID 均为普通字符串）：

1. 前文件定义 `audit_trinket`，`quest_uses=2`，引用不存在的 `missing_buff`。
2. 后文件再次定义 `audit_trinket`，`quest_uses=7`，`buffs=[]`。
3. 游戏应跳过第一条，再由第二条提供定义；编辑器仍选择第一条，而且没有报告冲突或缺失依赖。
4. 隔离 DSON 提交实际写入 `quest_uses_remaining=2`，而有效定义应为 7。只有第一条、没有后续定义时，编辑器仍会列出游戏不接受的饰品。

还验证了实际保存前的变化：先用存在的 `audit_buff` 完成预览，再把可读 Buff 文件改成 `{"buffs":[]}`，保持饰品文件及清单不变。刷新指纹能发现变化，但重新加载饰品目录仍返回原条目，`CommitAsync` 也接受了旧预览。Base、本地 Mod、工坊 Mod 三种来源均复现；这是饰品依赖筛选和写入重检的缺口，不是同步计时器没有发现变化。

建议：在同 ID 首条选择之前，根据有效 Buff 定义筛选普通 Buff 依赖；预览和提交使用相同结果。必须区分“确认缺少 Buff”与“Buff 来源读取失败”，并保留已经验证的文件覆盖及 Buff 重复定义规则。本轮只确认普通 `buffs` 缺失这一分支；没有把状态饰品其他 Buff 列表或 `remove_if_not_active` 条件一并宣称为已完整验证。

历史定位：`4e1db6b` 已接入职业依赖筛选和饰品首定义选择，但没有实现本项 Buff 依赖筛选。当前证据证明更新后游戏存在此规则；没有同一条分支的旧、新程序对照，不能断言这是最近游戏更新才引入的语义变化，也不能归因于本次 `f053d28`。

## 2. P2：饰品职业要求使用原始字符串，误淘汰游戏接受的条目

位置：`TrinketCatalog.cs:121–127`。

`heroIds.Contains(value.GetString()!)` 比较完整原始字符串；游戏对职业要求先计算到 NUL 为止的字节哈希，再查已注册职业。这里需要保留大小写差异，但“区分大小写”不等于“原始字符串必须完全相同”。

反例：已注册职业 `Az`，饰品要求为 `BE`。两者哈希都是 3567，游戏能找到同一个已注册职业；编辑器却记录“requires an unloaded hero class”并跳过饰品。`Az\u0000tail` 也会在游戏中找到 `Az`，却被编辑器拒绝。

这不只影响是否显示：同 ID 的第一条饰品使用上述要求、`quest_uses=2`，后面还有一条无职业要求、`quest_uses=7` 时，编辑器会错误选择后者。两个合成档案通过真实 `PrepareTrinketEditAsync → CommitAsync → DSON decode`，确认保存的剩余使用次数为 7，而不是第一条有效定义的 2。单条定义、同文件重复 ID、不同文件重复 ID 均覆盖。

建议：以游戏实际注册身份的哈希核对职业要求，保留全部要求都须满足的条件；不要删除职业存在性检查，也不要恢复大小写不敏感比较、重命名实际职业或饰品 ID。这里只存在一个正常职业定义和它的引用别名，不是两个定义冲突，现有冲突保护不能解释这次漏读。

历史定位：`git blame` 将原始字符串存在性检查定位到 `4e1db6b`。`831b962` 后来修正首个 JSON 成员的读取，但没有补齐这里的引用身份处理。

## 3. P2：HP Buff 的类型和条件仍按字面拼写识别

位置：`HeroClassCatalog.QuirkDefinitions.cs:84–110`，后续条件消费位于 `StagecoachHeroCandidateFactory.HitPoints.cs`。

Buff 的 `stat_sub_type` 和 `in_mode` 参数已经使用哈希，但 `stat_type`、`rule_type` 仍直接与固定字符串比较。原生加载器将这些字段复制到 64 字节缓冲区后，按哈希查枚举表。

例子：

- `d:mbat_stat_multiply` 与 `combat_stat_multiply` 哈希相同；
- `b7ways` 与 `always` 哈希相同。

当基础 HP 为 20、该 Buff 的 `amount=0.5` 表示增加 50% 最大生命时，这些输入会解析成与正常写法相同的原生枚举，预期新人物满生命为 30。编辑器却把怪癖标为 `Unverified`，候选生成被“尚未验证的规则”阻止。已分别覆盖类型别名、条件别名、两者同时出现，以及 `no_trinkets`、反向 `afflicted`、`in_mode`、`lightabove` 的已支持条件。

这次证实的是误拦截，没有证实这组输入会悄悄写入错误 HP。正常拼写、已支持的 NUL、属性子类型哈希别名、非 HP 属性，以及真正错误的大小写对照，结果均符合预期。

建议：把已验证枚举按原生规则解析为内部类型，再交给现有 HP 计算和条件枚举；不能只放宽目录准入而让后续条件计算仍收到未识别的原始字符串。未知枚举、非有限数值及可达的非正 HP 保护继续保留。

历史定位：字面枚举分支至少从 `1a03bb42` 已存在；`37d9167` 修正了字符串、精度、属性子类型和模式身份，但保留了类型与条件的字面匹配。不能回滚其正确的精度和大小写修复来处理此问题。
