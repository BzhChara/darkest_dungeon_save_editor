## 1. P2：长露营技能 ID 会得到错误的解锁购买编号

### 触发条件和影响

当 `职业 ID + "." + 露营技能 ID` 的 UTF-8 长度超过 63 字节时，编辑器按完整字符串计算 `tree_id`；游戏解锁和检查这项露营技能时，使用固定缓冲区截断后的字符串计算编号。

结果是人物目录和预检仍显示可生成，候选人物也写入该技能，但 `persist.upgrades` 中的购买记录没有落在游戏检查的编号上。不能据此声称已解锁这项技能。这里确认的是购买目标不匹配，不是声称这些档案一定崩溃，或已验证所有游戏界面如何展示这类人物。

例如职业 `audit` 加上 58 个 ASCII 字母 `a` 组成的技能 ID：

| 项目 | 游戏使用的规则 | 当前编辑器 |
| --- | --- | --- |
| 组合名称长度 | 先截到 63 字节 | 保留 64 字节 |
| `tree_id`，按存档有符号整数显示 | `-1352435858` | `1335343655` |
| 解锁购买码 | `0` | `0` |
| 游戏查询目标的购买记录 | 需要前一编号 | 未写入 |

同一例子把技能 ID 缩短到 57 个 `a`，总长恰好 63 字节，两边编号相同。`audit` 加上 20 个“营”字时，总长度只有 26 个字符、却有 66 个 UTF-8 字节，也复现错误；不能用 C# 字符数替代字节数。

### 当前代码路径

- [购买计划构造](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroCandidateFactory.Progression.cs)，第 55–58 行：直接拼接完整 `<class>.<camping skill>`。
- [持久化编号](../../src/DarkestDungeonSaveEditor.Core/StagecoachHeroSaveEditor.cs)，第 190–210 行：检查非空及单字符购买码后，对完整 `TreeId` 调用 `HashName`。第 257–261 行将结果写入 `tree_id`。
- [实际预览入口](../../src/DarkestDungeonSaveEditor.Core/SaveEditService.StagecoachHeroes.cs)，第 314–317 行：用同一个 `BuildUpgradePurchases` 重新计算计划；它能发现内容变化，但不能独立纠正这个编号规则。第 111–116 行把计划交给 `StagecoachHeroSaveEditor.AddCandidate`。

隔离程序实际调用了目录读取、人物生成、`AddCandidate` 和现有 Java DSON 编解码器。它没有调用面向真实档案的完整提交事务；上述预览入口的结论来自代码追踪。

### 原生依据

固定依据为 Windows x64 build 27890，游戏 EXE SHA-256：

`35E5A653279992564809FF8406FEBD5A02A7D6961044781B1296B38A7096F59B`。

1. 露营定义加载 `0x1404A4AF0`：技能显示名称复制到 64 字节缓冲区，见 `0x1404A51BF`–`0x1404A51D5`；技能注册 hash 另外从原 JSON C 字符串计算，见 `0x1404A521B`–`0x1404A5241`。二者不能混为“所有技能 ID 都截到 63 字节”。本轮反例的技能 ID 本身最多 60 字节，区别来自后续拼接。
2. 该加载器为适用职业创建购买树时，用 `%s.%s` 拼接职业与技能名称，调用 `0x14036B3A0`；见 `0x1404A5FE3`–`0x1404A6051`。
3. 格式化辅助函数 `0x14036B3A0` 给 `__stdio_common_vsnprintf_s` 传入 64 字节容量、截断模式，并在 `+0x3F` 写入 NUL，见 `0x14036B3CB`–`0x14036B3F2`。
4. 实际解锁 `0x1405C7940` 和检查 `0x1405C7A20` 也通过这个辅助函数构造树名，再按得到的字节计算 hash。因此问题不限于定义中的显示名称。

新提取的 [原生片段与探针](../../workspaces/historical-rule-review14-20260911/)包括 `native_1404a4af0.txt`、`native_14036b3a0.txt`、`native_1405c7940.txt`、`native_1405c7a20.txt`。验证脚本还直接调用本机 UCRT 对照同样的 64 字节格式化过程，确认 ASCII 和 UTF-8 边界；没有在游戏进程中调用这些函数。

### 历史来源及修复边界

`git blame -C -C -C` 将无界拼接追溯到 `a07b5c0d`（`feat: complete hero quirk and skill generation`）。`827ca422` 拆分文件时保留了它。`bfd0afb6` 后来移除了持久化前的 `Trim()`，但此前已经对完整树名计算 hash；恢复 `Trim()` 不会修复本轮反例。

建议在露营购买目标构造及对应校验处落实原生字节边界，核对截断后的重复目标与碰撞。应保留资源本身的技能 ID 和其他资源各自的身份规则，不能全局把 `HashName` 的输入都截到 63 字节。若选择对暂不支持的输入明确拦截，也应在目录可用性和生成预检一致给出原因，不能继续声称已成功解锁。

本轮未扩展验证所有战斗技能、装备树、超过原生缓冲区的职业 ID、截断切开 UTF-8 字符或多个技能截断成同一树的完整行为。修复时应明确这些边界，不用本轮单技能样例推导任意碰撞可以安全合并。

## 2. 已排除的疑点：露营解锁购买码 `0` 应保留

游戏确实会从露营 JSON 的 `upgrade_requirements` 建立升级需求，入口为 `0x1404A607B` → `0x140470460`。但人物的露营技能解锁和拥有检查并非简单选取该数组的任意购买码：

- `0x1405C79F0` 在解锁记录中明确写入 `0x30`，即字符 `0`。
- `0x1405C7AC6` 在查询键中同样明确写入字符 `0`。

因此“定义里允许其他 code，就应该把人物生成的露营购买码改为该 code”的推测不成立。这条既有规则不应删除，也不能套用战斗技能升级树的通用购买规则。

隔离样例另含 `upgrade_requirements.code = "A"` 的短 ID 对照，编辑器保持写入 `0`；预期来自上述原生解锁／查询分支，而不是仅由当前编辑器行为反推。未验证该特殊定义在露营训练界面的全部交互。
