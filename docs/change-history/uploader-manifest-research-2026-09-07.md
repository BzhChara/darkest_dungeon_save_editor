# 官方上传工具生成清单的隔离研究：2026-09-07

用户提出：用官方上传工具的规则，为无 `modfiles.txt` 的 Mod 补清单，再统一按有清单的 Mod 读取。用户确认先做隔离研究，再决定是否接入编辑器。本轮只修改新建测试副本和研究记录；未修改正式编辑器代码、安装目录内的 Mod 或真实存档，也没有提交到创意工坊。

## 结论

**官方生成清单不是无条件保留原加载行为的转换。**当前上传工具的 `dont_submit` 模式会排除与基础 data 目录逐字节相同的文件，并执行项目保存、本地化编译和地图编译。清单生成规则可以作为文件发现研究的证据，不能直接用于自动修补所有已安装 Mod。

“与原版相同”不等于“没有覆盖作用”。例如原版物品堆叠为 12，低优先级 Mod A 改为 99，高优先级 Mod B 提供原版文件以恢复 12。若 B 的清单省略这个文件，普通路径查找会继续采用 A。这是本轮实际生成的清单与此前已验证的游戏查找规则组合得到的反例；本轮没有重新进入游戏实测这组 12/99 数值。

在真实“水月怪物强化”的副本中找到 96 份与原版逐字节相同的文件。不能从这个结果判断作者意图：可能来自整目录复制、修改后恢复，或有意覆盖其他 Mod。本轮未调查作者的设计说明。

## 工具与隔离方式

- 工具：`E:\Steam\steamapps\common\DarkestDungeon\_windows\win32\steam_workshop_upload.exe`，21,515,264 字节。
- SHA-256：`b8b74103921a421c73d141b5632964932bd6425f299cf13e3e3eb4e8b2452020`。
- 只运行明确设置为 `dont_submit` 的项目。静态核对模式 3 跳过 Steam 创建/提交分支；[官方指南](https://steamcommunity.com/sharedfiles/filedetails/?id=819597757)也说明此模式用于不提交工坊的本地构建。
- 使用复制的 EXE 和已有依赖 DLL，在新建 ASCII 临时目录运行。研究输出归档到项目的 `workspaces/uploader_manifest_research_20260907/`。
- 基础 data 目录也是隔离副本：包含对应原版文件、基础颜色定义和默认封面。工具的可写 Mod 设备始终指向新建测试副本。
- 真实 Mod 副本保留原 `PublishedFileId`、标题和其他项目字段，仅在执行前改副本的 `ModDataPath` 与 `UploadMode`。对照基线取自该准备步骤之后，因此表中“工具改写 project.xml”不把准备步骤混算进去。
- 原版输入、工具及两个真实 Mod 均核对前后哈希；原始文件保持不变。没有启动游戏或安装测试 Mod。

### 与原版相同的文件

人工样例的四个文件均被日志明确归入 `Detected 4 unchanged files`，文件仍保留在副本中，但不在生成的清单里：

- `heroes/crusader/crusader.info.darkest`
- `heroes/crusader/crusader.art.darkest`
- `inventory/base.supply.inventory.items.darkest`
- `dungeons/weald/weald.1.mash.darkest`

水月副本日志报告 96 个未改变文件，逐项哈希核对成立：79 份怪物目录文件、8 份特效文件、9 份地区目录文件。地区目录中包含 8 份 `.mash.darkest` 和一份 `.original` 文件，不是 9 张有效战斗表。怪物目录样本包含原版 `.art.darkest` 和 `tint.png`。

### 目录与路径行为

人工样例确认：

- 点号名称、包含 `_template` 的路径组件和中文资源相对目录没有进入输出清单。
- 普通文件名仅设置 Windows Hidden 属性，仍然会被列入。
- ASCII 空格文件名可以列入；测试中的子目录条目排在当前目录文件之前，同层文件名大小写顺序与已观察原生枚举相符。没有由一个样例推断全部资源加载器顺序。
- 无扩展名样例未列入；`README.txt` 和 `scratch/source.cs` 则被列入。清单并不等于经过语义校验的游戏定义集合。
- `café` 相对目录生成单字节 `E9`，不是 UTF-8；该行大小为 0，实际样例文件为 68 字节。此项不能宣称已经正确支持，也未在游戏中测试其后续加载结果。

这也说明，借用官方工具并不能自动解决之前“水月中文分类目录是否被实际加载”的差异。其中文目录在本轮官方枚举中同样未列入。

`999 date Trinket` 副本只增加清单，工具改写项目和日志；本轮没有发现其原有资源内容改变。

水月副本：

## 验证过程中的失败与修正

- 首轮从中文宿主路径运行，工具返回 0 但没有生成清单；移到 ASCII 临时路径后流程才执行。没有独立还原该路径问题的全部编码原因。
- 首次创建 ASCII 临时子目录遭沙箱权限拒绝；按权限流程重试后完成，未改用其他手段绕过限制。
- 初始隔离 `project_paths.txt` 使用绝对路径及后续带换行的相对路径，未正确注册原版对照。静态检查及原文件字节确认该配置应为不带换行的相对路径。初始两份“原版文件仍列入”的输出属于无效原版对照，不用于结论。
- 修正为 `../base/` 后，默认封面复制与 `Detected 4 unchanged files` 两项控制同时成立，随后才运行真实 Mod 副本。
- `analyze.py` 可执行断言通过：省略项哈希、清单可解码路径的文件大小、预期编译改动、两个编译错误记录、覆盖提供方及四项换行差异均已核对。断言通过不代表那两个原生编译错误已修复。

有效执行目录分别为 `run_20260907_224238_676034`、`run_20260907_224339_104747`、`run_20260907_224346_414438`；其 `before.json`、`after.json`、`result.json`、源哈希、原生输出和副本均保留。总分析为 `analysis.json`，原生代码段为 `uploader_*.txt`。

## 后续方向

后续用户明确选择按官方工具排除原版相同文件，并授权补齐真实 Mod 清单。已采用隔离封装、仅还原清单路径的方式完成，详见[缺失清单补齐记录](official-modfiles-2026-09-07.md)。下文保留本轮隔离研究结束时的建议；不再代表用户的最终选择。

本轮建议保留“统一文件发现入口”的目标，但不要直接给真实 Mod 自动运行上传工具。可研究只在编辑器工作区保存文件索引；无清单来源不因“与原版相同”而被排除，也不触发本地化或地图编译。

内部索引仍须保留物理目录设备与清单设备的区别：原生枚举结果不能直接充当无清单设备的文件打开白名单，因为某些定义会构造路径直接打开。缓存也不能替代 Mod/DLC 挂载顺序、各资源加载器的解析规则和最终引用验证。

本轮未接入任何正式编辑器功能，未新增依赖，未重新构建产品或触发完成审阅。研究不宣称已完成“全部游戏资源”的读取，也不宣称全地区战斗新建/替换已经重新实机验收。
