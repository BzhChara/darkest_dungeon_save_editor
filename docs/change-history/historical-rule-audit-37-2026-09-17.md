## 提交与边界

先提交上一轮修复、测试、规则说明及第三十六轮审核记录：`619c5357f5f84f28801d669f62701688eff78497`（`fix: preserve dependency uncertainty and resolve native quirk references`）。提交前核对上一轮验证记录的 17 个任务文件、4 个程序集及 3 份通过日志，共 24 项哈希全部一致，`git diff --check` 通过；提交后工作区干净。

随后进行只读审核。本轮确认 **4 个需要修复的分支，均为 P2**，共同问题是有效文件读取失败后丢失了该加载位置的不确定性。正常文件下已经验证的 first-match / last-match 规则无需因此撤销。四处问题分别影响怪癖、人物升级、饰品实例次数和副本物品堆叠；以下保存结果来自隔离档案的实际 DSON 编解码与提交。

## 1. P2：怪癖定义读取失败会恢复旧 HP、互斥和进化配置

位置：`src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.cs:122–147,255–262`；保存校验在 `SaveEditService.StagecoachHeroes.cs:249–287,342–365`。

怪癖文件读取异常仅加入 `Issues`，没有占据未知的加载位置；`effectiveQuirks` 仍从读到的条目选最后一条。上一轮为 Buff 文件增加的完整性传播不覆盖怪癖文件本身。

复现：`a.quirk_library.json` 的 `other` 引用生命 +50% 的 Buff，没有互斥和进化；后面的 `z.quirk_library.json` 更新同 ID 为生命 +100%、排斥 `companion`、12 周后进化到 `companion`。两个 Buff 文件始终完整可读，人物基础 HP 为 20。

- 完整读取时，`other` 的 HP 为 40，与 `companion` 同选会被拒绝，初始进化时间为 12。
- 独占打开后一文件，使编辑器暂时读不到它，目录仍采用前一文件，允许 HP 30、进化时间 0 的候选。
- 从所有文件可读的健康状态开始：先让后一文件是空怪癖列表，生成含 `other`、`companion` 的 HP 30 预览；再更新后一文件并占用。重新预览和提交旧预览均通过，实际 town 存档含两个互斥怪癖、`current_hp=30`、`evolution_duration_remaining=0`。
- 释放文件后，不再改动定义，目录恢复 HP 40、互斥和 12 周配置。资源指纹也确认定义已经变化。

Base、本地 Mod、工坊 Mod 的保存结果一致；六种来源的目录对照均复现读取失败后的可写状态。失败发生在前面、后面已有完整同 ID 定义的对照仍能正确恢复最终值，所以不应把任意诊断都当作整目录禁止使用的条件。

历史定位：这段捕获后仅记录日志的怪癖路径从初始提交 `7b9a67f` 已存在。`619c535` 修的是 Buff 文件完整性和怪癖引用哈希，没有改这段读取失败处理；这是相邻分支的旧遗漏。

建议：把怪癖文件读取失败的位置传播到有效怪癖、互斥、进化链、HP 和写入可用性；后面明确的完整定义可以重新确认对应 ID。保存重读必须携带该状态，不能只比较成功读到的定义。

## 2. P2：升级树读取失败会恢复旧升级条件，并实际写入不符合新条件的装备

位置：`src/DarkestDungeonSaveEditor.Core/HeroClassCatalog.Progression.cs:19–68`；与第一项共用人物预览及提交校验。

升级树的单条无效 requirements 已经保留 ID 并标记不可用，但整个文件无法读取时只记录日志，`result` 中较早的同 ID 树仍保留。因此“字段解析失败”和“整文件读取失败”处理不一致。

复现：英雄等级为 1，基础护甲 HP 20，升级护甲 HP 40；早先的 `progression.armour` 允许等级 1 购买，后面同 ID 树把门槛改为等级 4。

- 后一文件为空时，健康预览正确得到护甲 rank 1、HP 40。
- 把后一文件改为等级 4 条件并暂时独占，重新预览和提交旧预览仍通过。
- DSON 回读确认 town 写入了 `armour_rank=1`、`current_hp=40`，upgrades 也写入了对应护甲购买记录。
- 释放文件后，当前完整目录生成同一等级英雄得到 rank 0、HP 20。

Base、本地 Mod、工坊 Mod 均复现。另三组对照在最初已读到新条件时会拒绝被占用后的旧结果，三份人物存档保持原字节；因此问题不是所有目录比较都失效，而是失败后剩余结果恰好等于原预览。

历史定位：`3d2bd9c` 接入“升级树按最后匹配完整定义”时保留了只记录整文件异常的路径。最后匹配规则本身仍符合研究；缺少的是读取失败后的未知状态，不能用恢复旧的文件名猜测或 Mod 优先级兼容修复。

建议：升级树候选解析也传播失败位置；绑定武器、护甲和技能购买目标时，区分确认没有树与树来源未完整读取，并验证生成、购买记录、HP、预览和提交的一致性。

## 3. P2：饰品定义文件读取失败会采用后面同 ID 的实例次数

位置：`src/DarkestDungeonSaveEditor.Core/TrinketCatalog.cs:43–46,189–192,313–324`；预览与提交在 `SaveEditService.Trinkets.cs:44–66,299–366`。

饰品依赖的“确认缺失／无法确认”已修复，但饰品定义文件自己的读取失败仍仅写日志。前面的有效文件读不到时，后面同 ID 定义就变成第一条，并被标为可写。

复现：`a.entries.trinkets.json` 首条 `audit_trinket` 的 `quest_uses=2`；后面另一文件同 ID 的次数为 7。两条都不引用 Buff 或职业，排除依赖保护的干扰。

- 正常读取选择 2。独占打开前一文件后选择 7，`HasProviderConflict=false`。
- 健康预览最初在前一文件为空时使用 7；随后前一文件新增有效次数 2 定义并被占用，重新预览和旧预览提交仍获准。
- 实际 estate 存档写入 `quest_uses_remaining=7`，释放文件后目录重新选择 2。

六种来源的目录对照及三种来源的保存均复现；占用后面的文件、首条仍完整可读的对照继续正确选择 2。这里不能简单规定所有读文件异常都禁用全部饰品，也不能因为没有读到前面的定义就证明后面的定义获胜。

历史定位：`ScanFile` 的仅日志异常处理从初始提交 `7b9a67f` 已存在；近期 `3f3db14`、`619c535` 修的是依赖淘汰与依赖完整性，没有覆盖饰品定义文件读取失败。

建议：在 first-match 选择时保留失败的文件槽位及未知定义范围，后方受影响的候选应只读，保存重读同样检查。已证明位于所有失败槽位之前的有效首条可保留使用。

## 4. P2：普通物品读取失败保护只覆盖“仅存档”，仍可按错误堆叠上限保存

位置：`src/DarkestDungeonSaveEditor.Core/QuantityItemCatalog.Definitions.cs:97–101,278–284`、`SaveEditService.QuantityItems.cs:54–76,376–424`。

普通物品已经收集 `readFailures`，但只有 `IsSaveOnly` 分支检查完整性。失败文件后面的另一条同 `(type,id)` 定义仍会作为正常可写物品；其上限能够通过预览与提交前的再次读取。

复现：副本物品 `estate/probe_token`，首文件上限 2，后文件同身份上限 8，背包容量 32。

- 全部可读时上限为 2；占用首文件后目录仍允许按上限 8 修改，同时诊断列表其实已记录读取失败。
- 健康预览在首文件为空时将目标数量设为 10；首文件随后新增上限 2 定义并被占用，重新预览和提交旧预览仍通过。
- 实际副本 DSON 存档分配为 `[8,2]`。释放文件后，上限恢复为 2，同样目标数量的正确分配为 `[2,2,2,2,2]`。

Base、本地 Mod、工坊 Mod 均复现。首条始终完整、只有后文件读不到时，上限仍正确为 2；最初预览已经采用 2 的对照会拒绝占用后的不同结果，存档字节不变。

历史定位：原始捕获路径来自 `dca5b2b`；`dac3dbb` 为缺失获胜文件与仅存档条目补充 `readFailures`，但没有覆盖仍存在另一份同身份定义的分支。此前同路径缺失不恢复下层文件的修复仍有效；本次是不同文件之间重复身份的选择遗漏。

建议：first-match 完整性必须同时影响有定义条目和仅存档条目；目录、增量刷新、预览、提交按同一规则标记受影响项，确保背包分格使用已确认的上限，不改动钱包聚合或小镇／副本身份规则。

## 共性与修复边界

四项都经过“正常读取并建立预览 → 更新另一有效定义文件 → 暂时无法读取该文件 → 再预检与提交”的路径。`modfiles.txt` 内容及 Mod 顺序没有变化，其他可读文件继续产生与原预览相同的结果，读取异常又没有进入可用性/目录结果校验，因而错误通过。不是用探针伪造一个历史损坏候选再提交。

自动同步读取资源指纹时可以报告读取错误，但同步调度不能替代保存服务自己的完整性校验。探针确认释放锁后指纹确实变化；本轮没有把共享同步的正确错误处理视为这四个保存分支的可靠保障，也没有建议靠缩短轮询周期处理。

建议一次修正这组资源读取完整性传播：保留失败槽位，按消费规则判断哪些候选仍可证明，覆盖首次加载、更新期间预检、旧预览提交、恢复可读和不受影响候选。无需增加旧存档兼容，也没有证据支持删除清单限制、同路径获胜者规则或正常 first/last-match 行为。
