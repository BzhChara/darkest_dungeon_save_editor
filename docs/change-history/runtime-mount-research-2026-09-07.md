## 无清单扫描问题的前后区别

以下说明对应用户追问的既有修复，并非本轮另做了一次产品修复。

旧实现先根据档案的启用记录定位内容来源。对无 `modfiles.txt` 的 Mod，在标准资源目录和启用 DLC 对应子目录中按文件类型递归查找。例如怪物查找 `monsters/**/*.info.darkest`，物品查找 inventory 下的物品定义，饰品查找 trinkets 下的 entries 文件。

旧怪物解析从文件名去掉 `.info.darkest` 得到 ID，把扫描到的物理文件按来源优先级分组，直接读取这些文件的体型和 Boss 标签。其缺口在于：文件出现在扫描结果中，不等于游戏后续会使用这个物理文件作为该 ID 的定义。

现实现分开处理两个阶段：

1. **发现 ID。** 清单来源按照清单枚举；无清单来源按照已验证的物理目录规则枚举，跳过点号名称、包含 `_template` 的路径组件，以及本机游戏默认 C locale 下无法完成转换的资源相对路径。
2. **解析有效定义。** 对支持的怪物 ID，去掉末尾两个字节得到 family，再构造 `monsters/<family>/<id>/<id>.info.darkest` 和 `.art.darkest`。分别解析这些标准路径的有效提供方，按 info 后 art 读取。有清单的 Mod 仍必须列出相应标准文件；发现一个分类目录的文件，不会使未列出的标准覆盖自动生效。

实际例子：

```text
扫描发现位置：
monsters/游荡/bulrush/bulrush_E/bulrush_E.info.darkest

ID 对应的标准定义位置：
monsters/bulrush/bulrush_E/bulrush_E.info.darkest
monsters/bulrush/bulrush_E/bulrush_E.art.darkest
```

分类目录文件不能直接替代后面两个标准文件。对于本次“水月怪物强化”的 15 个多读 ID，物理扫描对 `monsters/游荡/...` 的路径转换差异也是直接原因：旧编辑器的 .NET 文件枚举能找到它们，游戏在已验证的默认编码环境下跳过这些路径。现在使用统一物理发现过滤，差异消失；没有按 Mod 名称或这 15 个 ID 编写黑名单。

不能把这个结论扩大为“所有中文 Mod 都不可用”：显示标题与资源路径是不同字段，清单枚举和标准路径打开也不是同一分支。清单中明确列出的中文路径不套用物理发现过滤。特殊字节 ID、其他 locale 等仍保留已记录的限制。

编号计算与能否放置也分开。游戏已分配的空怪物类可能以体型 0 影响遭遇表的行位置；编辑器保留其编号影响，但不会仅凭空类就允许直接放置或用作 Bridge 来源，避免把后续正常组合的编号挤错。

本轮从游戏挂载表再次确认，“水月怪物强化”对应 `mods/Shuiyue_Monster_Enhancement/`，原生清单指针为零、Mod 库已解析文件数为零，确实使用物理目录分支。磁盘检查也确认它没有清单。
