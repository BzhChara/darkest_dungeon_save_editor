# Quest board: saved data and UI

The town version of the Battle tab displays and edits the **saved quest board**. Load a town profile and wait for synchronization, then open **Quest Board**. Before loading, the board displays a load prompt and its controls are disabled. Raid profiles still use the existing battle map. Creating, replacing and deleting quests produce a guarded preview, ask for confirmation, back up the profile, write the quest save, then synchronize before enabling another operation.

`ProfileCatalogSnapshotReader` decodes a stable copy of `persist.quest.json` with the existing native save codec. Saved slot keys, IDs, generated/plot identity, type, difficulty, length, goals and completion/retention reward inventories come from that file. The reader never regenerates or rerolls rewards. Metadata, localization, map positions and artwork use only the profile's active base/DLC/Mod sources and existing native manifest/overlay lookup. No game artwork is bundled. Mod regions with saved quests use their layout records; a missing position leaves the quest accessible through a separate selector instead of inventing coordinates or dropping the entry.

Unchanged synchronization reuses the board. Quest-file, progression-file or content changes rebuild it, and unloading or switching profiles clears the old selection. This uses the existing shared synchronization boundary, with no new background polling. English/Chinese switching updates names and descriptions immediately.

## Region visibility

The editor keeps native always-visible regions available even when empty. For regions with `requires_quest_to_display: true`, it also exposes empty destinations referenced by an active plot quest or a nonempty `generation.type.available_quests_table` entry. This lets users create quests in real destinations without displaying internal scenes or unused layout placeholders. The reader opens the effective canonical `dungeons/{id}/{id}.dungeon.json` and quest resources through the existing active-source and manifest lookup. Plot destinations use the quest constructor's first definition for each native identity; generation entries require a typed quest row. Natural progress requirements do not hide these destinations. Layout-only entries without a readable definition do not introduce empty regions. Every saved quest still introduces its region, even if its definition or entry template is unavailable.

The game itself hides empty regions when `requires_quest_to_display` is `true`. The editor deliberately keeps real empty quest destinations such as town and Vermintide's `vmt_sewer`, which has both plot and generated quest entries. Farmstead and `vmt_mine` set the flag to `false` and remain visible. `is_released` is not a visibility filter: the game also uses it for locked-region presentation and tooltips.

In the installed Mods examined on 2026-10-28, Vermintide (Workshop `2683922974`) supplies `farmest` as a layout/region definition with no quest entry; `vmt_town` likewise has no entry, while the actual sewer quests target `vmt_sewer`. `town_wave` belongs to Sunward Expansion: The Night Parade (`2115544857`), and `ship_wave` to The Sunward Isles (`1689234891`). They appear in `scripts/raid_settings.json` as wave-transition scenes, not quest destinations. These empty scenes do not display or contribute to content-centered framing. The filter uses active quest definitions, not these IDs, suffixes, or the presence of translated names: a Mod adding an actual quest entry, or an existing saved quest, makes the region visible.

Regions sharing exact map coordinates use one dropdown at that location. Only the chosen region's markers are shown; selecting a saved quest selects its corresponding region. The native town and Vermintide sewer share `(1260, 750)` and exercise this behavior; `vmt_town` joins them only if it has a quest entry or a saved quest. Other regions keep their normal clickable headings. Native evidence: `0x1404B0A8E` constructs the canonical definition path, `0x1404B0D0E`–`0x1404B0D30` reads the display flag, and `0x14068C106`–`0x14068C158` skips an empty region only when that flag is set.

Region headers use the native progression/no-progression artwork according to `.has_visible_progression`. For visible progression, skull numbers and the progress bar come from `persist.progression.json` (`base_root.dungeon.{id}.xp`) and the effective canonical `campaign/progression/progression.json` thresholds. An absent dungeon entry has zero XP; missing progression data is shown as unknown rather than a fabricated zero. The native level lookup at `0x140564F70` stops at the first threshold greater than the saved XP. The shipped table is `[0, 2, 6, 10, 16, 22, 32, 42]`.

Quest selection uses the full native 192-by-192 `quest_select_selected.png` texture at its native offset, with a fresh random rotation on selection. The native executable loads this one texture at `0x14062244E`, selects an angle at `0x140693740`, and renders it at `0x14068D75F`; the different-looking splatters are rotations, not separate shipped image variants. Refreshing the view retains the selected angle.

The board has an independent detail pane on the left and the native map background on the right. The detail pane uses about 30% of the available width, bounded between 240 and 280 device-independent pixels, without a resize handle. The width cap keeps the details close to their original reading size as the window grows, leaving the extra space for the map. The embedded map opens at **50%**, centering the combined region headers, progression bars and quest buttons horizontally, with background overflow clipped to the existing viewport. Its vertical reference is fixed at native map Y=487, preserving the town view framed between the Darkest Dungeon header (Y=90) and the end of town's first quest row (Y=884). Switching between town and sewer, changing selection or changing quest counts does not recalculate this vertical reference. Resizing and zooming still transform it with the map, and manual panning remains available above the minimum. Transparent region hit areas and rotating selection splatters do not affect horizontal framing. Native region coordinates stay unchanged, and the background moves with the markers. The main window is 1460 by 920 device-independent pixels. The embedded zoom minimum is 50%, or the whole-image fit scale if a larger viewport requires it. Embedded **Fit** restores the horizontal content center and the fixed vertical reference at that minimum; it cannot shrink the map below 50%. If the viewport is too small to contain the content at 50%, overflow is clipped. Use **Full map** to view the complete background. Map zoom does not shrink the details. Content is inset from the top and bottom frame lines, which are drawn above both panes so the map cannot cover them.

- Click a quest to inspect its description, objective, and saved rewards. In the embedded view, the detail panel starts at the quest's red title band, omitting the estate-map icon and heading. It displays the quest/reward portion of the native `quest_select.questverbose_bg.png` at its original proportions, with text aligned to the game's layout coordinates. The editor defaults to a 1460 by 920 device-independent pixel window, with the 1120 by 720 minimum unchanged. The panel scales to its independent pane's width and scrolls vertically when its contents exceed the available height. Reward icons use native inventory slots, quantity overlays, and rarity frames; additional rows scroll inside the original reward area. Wheel input over details scrolls their contents without zooming the map.
- Right-click an existing quest for **Replace** and **Delete** only. Right-click the region's empty marker area or its heading for **New** only. The provisional type categories are unchanged; their contents now come from active game definitions, including custom Mod types. The board has no plus, undo, or reset buttons.
- Right-click elsewhere on the map for **New → region → type** as an alternative to a region's own menu. The unpositioned-quest selector also exposes Replace/Delete for its selected quest.
- The picker filters actual templates by difficulty and search text. The chosen definition determines its icon, goals and length. Missing dependencies show an unavailable reason. Presentation samples remain explicitly enabled only in UI contract fixtures and are never populated by loading a profile.
- The mouse wheel and right-button drag zoom and pan the background and markers together. At minimum scale, the map cannot move; after zooming, panning stops at each edge so the minimum-view rectangle remains covered, including its clipped overflow. Before manual zooming or panning, resizing and content refreshes reapply horizontal content centering and the fixed vertical reference with the embedded 50% floor. Framing is clamped to the background edges to avoid exposing empty space. The minus button and mouse wheel enforce the same lower bound. 100% sets the shared scale, subject to that minimum. Full map keeps its existing whole-image centering and window sizing, starting from 1600 by 820 device-independent pixels and adjusting around a whole 16:9 map rectangle. Its separate minimum follows the viewport and can be below 50% in a small full-map window. Closing it restores the embedded view's previous default, fit, or manual zoom/pan state. Returning to the tab and changing language preserve that state as well.
- New, replacement, and deletion menu graphics and styles, toolbar controls, and dialog styling follow the existing battle map. Operation messages use the main window's activity log, with no separate board status strip.
- Full map occupies the same toolbar position and uses the same primary-button dimensions and spacing as the battle view's Force return to town action. The full view restores the native estate-map icon and heading above the quest details; closing it restores the compact embedded layout and keeps the selected quest.

The toolbar shows the saved task count. Interaction requires a loaded profile and the same ready, idle, game-stopped state used by the battle view. Game exit alone does not unlock the board: synchronization must finish first. Scene changes switch between the real town board and the battle map. Opening menus and browsing choices do not scan resource hashes; the guarded preview and commit perform the expensive checks.

The current reward area shows the saved completion and recovery inventories; wave threshold reward schedules are not displayed as immediate rewards. Missing localization falls back to the other language or the saved ID; unknown saved goal definitions retain their IDs and emit a diagnostic. Camping follows the native quest-select display rules below; multiple provision files do not make the count unknown.

## Manual editing and persistence

- Manual creation and replacement bypass natural generation conditions, including plot dependencies, completion/repeatability, event history, dungeon/hero levels, inventory and recovery thresholds. This policy is specific to the quest board; event-attached quests keep their existing eligibility checks. Bypassing a generation condition does not change the game's entry, completion, reward or persistent-expedition rules.
- The catalog includes effective plot definitions and ordinary combinations from `available_quests_table` across progression levels. Ordinary difficulty choices come from `generated_resolve_level_difficulties` or the row's nonzero override. An omitted or zero `difficulty_override` keeps the generated difficulty, matching native `0x140574A25`. All-region and matching-region goal lists are concatenated in native order. Native hash identity and resource query precedence are reused.
- Ordinary rewards use the native difficulty/length item and XP matrices, dungeon heirloom choices/amounts, and weighted trinket rarity draws with same-award-category fallback. Plot completion rewards, threshold schedules, optional modifiers and retained inventory instances use the event quest initializer. Selection does not reroll rewards; rolling occurs once in the prepared copy.
- An unresolved type, dungeon, goal or required reward prevents correct initialization and blocks that template or preview with a specific error. Saved quest string identities must fit the game's 64-byte buffers. A plot already on the board cannot be appended under the same native identity; replacing its existing slot is allowed. Generated quests receive an unused `generated_N` identity.
- Deletion removes only the selected board entry. Replacement initializes the new quest and keeps the selected slot and position. Neither operation invokes failure/ignore settlement, advances the week, rewrites completion history, consumes retained items, changes `plot_quest_total`, removes persistent expedition files, or creates a Bridge. A previously explored persistent quest can therefore reuse its existing expedition when selected again; this is not a map reset operation.
- Only `persist.quest.json` is written. Preparation copies and guards game, quest, estate, roster and town saves because reward generation depends on those inventories. It verifies town state, active content, DSON roundtrip and revision. Commit checks for changes, backs up all recognized profile files including persistent expeditions, uses `GuardedSaveReplacement`, and recovers the original target after a failed replacement without overwriting another writer's changes. Controls remain disabled through post-write synchronization.

Native evidence for the installed executable below: quest restore and 64-byte identity buffers `0x140455D30`; goal selection `0x140456900`; generation resource parsing `0x14045E7E0`; generated reward calculation `0x140575000`; generated IDs `0x1405767F3`; plot construction `0x140576CC0`; board persistence `0x1405728C0`. The load loop enumerates saved object members rather than requiring contiguous slot keys. `plot_quest_total` is separate definition bookkeeping, not the current number of board entries. Local excerpts are in ignored `artifacts/quest-board-editing-20261027/`.

## Native camping display

The quest-select counter is computed independently of the eventual expedition's party-specific supplies:

1. Resolve the native `campaign/provision/.*provision.json` query and its same-path overrides. Append every effective file's `raid_starting_length_inventory_item_lists[length]` entries. An absent length bucket contributes nothing.
2. For a plot, append positive entries from `additional_provisions.items`. This runtime lookup retains the last plot definition with the saved native identity.
3. Append positive `starting_items` from each saved goal. The quest-select call supplies an empty hero list, so hero-specific provisions do not contribute here.
4. Remove items matching the plot's `disabled_provisions` pairs (`item_type`, `item_id`), then sum the remaining `supply/firewood` amounts using native inventory identities. The UI displays this integer, including zero.
5. The native random marker `x?` replaces the number only for a plot of type `wave` with a `survival` goal whose `data.amount` is zero. Color of Madness's `survive_endless` is the shipped example. Finite waves such as `survive_short` do not use this marker. Tooltips use the active localization keys `town_quest_number_of_campsN` or `town_quest_number_of_camps_random`.

Survival objectives also distinguish finite and endless waves: `town_quest_goal_start_single_survival` is used for every nonzero amount (for example, `survive_short` with 20), while zero uses `town_quest_goal_start_plural_survival`. Those keys mean finite/endless here, rather than the singular/plural quantity rule used by other goals. This branch is at `0x140809422`–`0x140809450` in the same executable.

Kill-monster objectives use the final listed monster's localized name and the plural template. The displayed amount is capped at the number of distinct resolved `shared_health` hashes (including zero) plus one per resolved ungrouped monster. Canonical monster info/art lookup supplies the effective health groups. Thus the shipped `kill_formless_flesh_A` target list has four body parts and a raw amount of four, but the shared `formless` group makes its objective `Kill 1 Inchoate Flesh.` This display-only calculation does not rewrite the saved objective or change the game's completion requirement. Native formatter evidence: `0x1408090BC`–`0x1408092E2`.

Evidence checked on 2026-10-27 against the installed x64 executable SHA-256 `9972B79F0EA892C82BF32CB1F4CF85A8E2B30270FCE219D60385C19013965EA9`: provision JSON loader `0x140451F10`; length append `0x140452A80`; plot append `0x140452B70`; goal append `0x140452EB0`; disabled-item removal `0x140453070`; random-camp predicate `0x140456380`; quest-select sum and display `0x14069149C`–`0x140691883`. The corresponding shipped examples are `campaign/provision/provision.json`, `com.quest.types.json` and `com.quest.plot_quests.json`. Local disassembly and read-only profile snapshots live under ignored `artifacts/quest-board-real-data-20261027/`. Reduced Mod fixtures verify the confirmed append and lookup rules; they are not claims of observed defects in a user's Mod.

## Validation

`--quest-board-data [snapshot.json]` checks native-shaped saved data, resource lookup, real-data UI binding, profile/selection/language refresh and shared snapshot invalidation. The optional JSON is a serialized `QuestBoardSnapshot` for offscreen rendering with actual installed artwork. `--quest-board-preview [game-directory]` retains the explicit presentation-fixture checks for layout, menus and zoom; pass an installed game directory to exercise artwork scaling. `--quest-board-edits [profile-copy]` checks creation, replacement, deletion, rewards, manual eligibility bypass, DSON, guards, backup/recovery and real-command dispatch. Its optional native profile mode clones the supplied profile, initializes available templates and commits representative operations only in the clone. These are offline checks; they do not constitute in-game validation of quest writing.

## Categories and native evidence

Menu labels describe the quest's actual `type`; they are editor labels, not a claim that the game presents this category menu. The base definitions are in `campaign/quest/quest.types.json` and `quest.generation.json`. Concrete plot entries are in `campaign/quest/quest.plot_quests.json`, the Crimson Court `crimson_court.quest.plot_quests.json`, and Color of Madness `com.quest.plot_quests.json`.

| Menu category | Native type | Concrete game example |
| --- | --- | --- |
| Exploration | `explore` | Explore 90% of rooms; the tutorial plot also uses this type. |
| Room battles | `cleanse` | Complete every room battle. |
| Gathering | `gather` | Collect three medicines in the Weald. |
| Use quest items | `inventory_activate` | Cleanse corrupted altars; Darkest Dungeon II activates beacons; the first Courtyard plot burns hives. |
| Direct interaction | `activate` | Darkest Dungeon III activates the portal. |
| Boss objectives | `kill_boss` | Regional bosses, the town invasion, and the Screecher's trinket-recovery plots. |
| Wave battles | `wave` | Farmstead introduction, Miller, and endless plots. The Miller's goal differs while the quest's type remains `wave`. |

Progression, event origin, repeatability, fixed maps, and generated/plot identity are independent properties and do not define these categories. For example, the tutorial is a progression plot but still an exploration quest; Darkest Dungeon I/II/III use three different types. The recovery plots are repeatable and use `kill_boss`, while the town invasion has the same type and is not repeatable. DLC type definitions also contain entries such as `kill_miller`, but the actual Miller plot uses `wave`; the preview follows the plot's `quest.type` instead of inferring a category from a goal ID.

Saved Mod quests retain their own type and ID, including types outside the provisional menu categories. Missing icons use the existing fallback graphic and keep their readable task label. Custom creation types receive their own group using the native type ID. The provisional labels can be revisited separately; unfamiliar types are not automatically unavailable.
