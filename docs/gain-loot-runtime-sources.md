# Runtime sources for gain_loot references

The quantity catalog follows potential paths from native consumers to Effects, Buff triggers and `.gain_loot` Loot tables. An Effect definition alone is not an entry point. `ConfirmedActive` means a verified potential content path; it does not predict the currently open party, random outcomes or actual drop frequency.

The baseline is the November 2026 [Ode to Mods update](https://www.darkestdungeon.com/news/darkest-dungeon-ode-to-mods-update/) and its [official feature list](https://docs.google.com/document/d/1zkAFFAiRS-q11wW06DiSHo5QSGyzACnXgr8CAxW1dfY), checked against Windows x64 `Darkest.exe` SHA-256 `f9d914ca1d7d9ad3ff4f151a46e4853e532ce1f5f109f700b0c1381a3f7e0d12`. Program evidence consists of static disassembly, loader/runtime calls and RTTI; official C++ source is not available. Addresses below are RVAs. Regression fixtures are isolated editor tests, not a live-game playthrough.

## Source rules

Native file queries are recursive and case-sensitive, including their unescaped regex dots. Local/Workshop files must be manifest-listed; enabled DLC mount rules apply before provider selection. Ordinary flags-0 queries replace same-path providers. Torch settings, districts and regional prop definitions use additive flags-9 queries instead. A malformed shadowed provider does not taint a flags-0 winner; a malformed additive input does affect completeness.

Building queries start at `campaign/town/buildings/`, using `.*<building>/.*<building>.building.json` for each registered building (`0x5429EC–0x542A3E`). Both `custom/tavern/tavern.building.json` and `custom_tavern/tavern.building.json` below that root feed the tavern consumer. The first directory segment is not the building identity. Discovery, same-path provider resolution, town currency references and activity Buff roots use this same rule; missing or malformed effective nested files affect completeness too.

Quirk definitions retain their ordered objects. Every positive float32 `random_chance` object can supply its own Buffs through random acquisition (`0x4EBCA0`); saved-ID, explicit Effect and evolution lookups instead select the last matching full hash. `quirk_act_outs` bind and append to the **first** matching object (`0x4EB901`), and the hero consumes the owned object's lists (`0x5D7F10`). Thus a shadowed zero-chance first definition cannot supply act-outs through a last-definition ID lookup, while a positive-chance first definition remains a valid random route. Hash aliases follow the same rules. This refines potential content reachability; it does not infer an arbitrary historical object from a saved ID.

Loading a torch setting does not activate its key. `default` and keys selected by an admitted flashback have verified activation paths here (`0x615050`, `0x772273`, `0x5CA9B0`). Other loaded keys retain their named Effect/Buff paths as uncertain until their quest, monster, wave or other selector is modeled; those paths can yield `AnalysisIncomplete`, never `ConfirmedActive` by loading alone. They do not advance a verified item-use prefix, revoke a verified default path, or make unrelated orphan definitions active. A separate possible prefix preserves uncertain item paths that such a selector might enable.

| Family | Recognized route and native behavior |
| --- | --- |
| Torch settings | `scripts/*raid_settings.json`, `torch_settings_data_table[].data`: hero/monster Buff and Effect lists. The last matching key replaces the entire value, even when lists are omitted (`0x4C13E0`, `0x4C16E0`). Key hashing uses 511 bytes; lists use 127-byte tokens. Transition Effects are noncombat. Item Buff application consumes only the first `supply`/`torch` entry (`0x430DD2`, `0x4310E0`, `0x4FCEC0`). Performer Effects accept usable typed inventory items; all matching entries contribute normal effects and the use-count-selected sequential list (`0x4FCF50`). |
| Quest modifiers | `campaign/quest/*quest.modifiers.json`, `modifiers[].hero_buffs` / `monster_buffs`; IDs are bounded to 63 bytes before hashing, and the last matching payload wins (`0x465DB0`). Valid condition kinds are `always` and `wave_kill_count` (`0x0633E0`, `0x616320`). Conditions represent possible quest states, not a filter on the current save. |
| Inventory use | Native inventory item query; first matching type/ID wins. `supply` and `estate` reach the generic use path. Torch performer callbacks take precedence over both `sequential_use_effects` and the same-name fallback (`0x42A2F0`); both sequences use the same typed use counter and retain their final step for larger counts (`0x4FD06F`, `0x5D73F7`). Item sequences take up to 16 tokens of 63 bytes. `torch` and `the_blood` have dedicated fallback callbacks; food/journal/quest types do not reach generic item Effects (`0x429750`). District `DistrictReplacementInventoryEffectBuffData` replaces the generic fallback by typed identity, with 63-byte fields (`0x451760`, `0x42A940`); it cannot bypass a sequence or performer callback. Unbuilt districts still permit the ordinary fallback path. |
| Curio Effect results | Native curio type CSV query and block parsing. `Effect` alternatives are separate weighted names at columns 7/10/13 (zero-based), not packed Loot IDs. Names use 63-byte tokens. Item interactions require the matching item identity (`item#type`, default type `supply`). These Effects run outside combat (`0x4E4639`, `0x4B2CC0`). |
| Shared combat rules | Shared rules query: `stun_onset_buffs`, `stun_recovery_buffs`, `stall_stress_effect_name`. Omitted fields retain earlier values; present arrays, including empty arrays, replace them. Runtime tokens use 63 bytes (`0x44F9F0`, `0x4F7A72`, `0x4F8672`, `0x5B3B30`, `0x5B3A76`). |
| Flashbacks | `raid/flashback/*.flashbacks.json`: starting Effects, `type=buff` results and completed-camp Buffs. Any available required class can satisfy admission (`0x4BD1E0`); an empty list cannot. Starting/result payloads use the first matching 63-byte flashback ID (`0x5A4570`, `0x5CAD96`); completed-camp Buffs visit all declarations independently of new-start chance (`0x5CB390`) and resolve full Buff-ID hashes without truncation (`0x4BCF30`, `0x5CB454`). Results require supported hero targets; `not_required_hero` needs an available class outside the required set. Starting Effects execute outside combat at `0x5A4654`. |
| Town activities | Known abbey/tavern/sanitarium activity factories, positive side-effect/result/choice weights and `type=apply_buff`, then `data[].buff_library_ids`. Arbitrary activity IDs or result types do not instantiate an ApplyBuff consumer (`0x534AB0`, `0x555DF0`, `0x54F830`, `0x536800`). Admission resolves the full Buff hash, while execution looks up its stored 63-byte token (`0x53C220`, `0x53C450`). |
| Trait/quirk act-outs | Effective campaign trait definitions and `shared/quirk/*quirk_act_outs.json` records attached to an existing quirk. Supported turn act-outs consume `data.string_value`; supported reactions consume `data.effect`. Positive chance, native behavior kind and available class restrictions are respected. Quirk act-out declarations append; empty lists do not erase previous lists (`0x4EB640`, `0x4932E0`). Effect names use 63 bytes. Camping/curio/trap reactions are noncombat; combat reactions and turn actions are combat consumers. |
| Traps | Reuse native prop resource resolution: Base-only root definitions, additive regional definitions, eager parent copies, omitted-versus-empty lists, and first/nearest difficulty selection. Subsequent curio registration can replace a prop's instance type. Only effective trap resources contribute `success_effects` / `fail_effects`, with 127-byte tokens. Both are noncombat (`0x714B80`, `0x70ECC0`). A Mod root `props/trap_definitions.json` is not a native source; a region path such as `props/crypts/trap_definitions.json` is. |

`last_hero.buffs` is also a verified potential source on both sides: 16 slots per declaration, 63-byte tokens, append semantics and termination on an empty/dot-prefixed slot. `0x5A95E0` checks for exactly one living non-corpse actor and applies the Buffs once; callers `0x5AEF23` / `0x5AEF5A` cover heroes and monsters. Monster `deaths_door` remains a separate, unverified activation path.

## Context and completeness

Noncombat Effects cannot directly produce `gain_loot`. They may install a persistent Buff whose later combat trigger reaches loot. The graph preserves that distinction and terminates Effect/Buff cycles. It does not turn every JSON field named `effect` or `buff` into a root.

Item sequence reachability starts at use count zero. A nonempty selected torch sequence advances that counter; a generic item sequence also advances it when no performer callback takes precedence. An ordinary fallback or normal-only torch callback does not advance it. Empty initial steps therefore do not make later sequence Effects reachable by themselves. Possible torch states share this analysis, and repeated final steps need no unbounded traversal. Historical save-only counters are not invented as extra roots.

Unreadable effective files, malformed relevant structures, failed provider discovery or unresolved consumed dependencies make the analysis incomplete. An item with no independently verified route is then `AnalysisIncomplete`, remains visible and cannot be certified `SuspectedUnused`. A verified independent route still yields `ConfirmedActive`; failures in one source family cannot erase evidence from another. Missing individual named Effects/Buffs are skipped as unresolved native lookups, rather than made into imaginary executable definitions.

This is a bounded content graph. It does not model arbitrary scripts, every hard-coded Effect, save-only pre-existing Buffs, or complete cross-expedition lifetimes. No game resources or player saves are changed by source analysis. See [content and save rules](content-save-rules.md#november-2026-official-program-compatibility) for the existing actor, trinket, Buff, camping, event, district and set roots.

The focused command is `dotnet tests/DarkestDungeonSaveEditor.ContractTests/bin/Release/net8.0-windows/DarkestDungeonSaveEditor.ContractTests.dll . --official-mod-update`; the same contracts are included in `--native-all`.
